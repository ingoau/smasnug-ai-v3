
# Slack Agent — Design Doc
2026-10-03 · @Ingo
## Overview
A workspace-wide Slack agent for the Hack Club Slack, built around a fast front agent that delegates longer work to background subagents. The focus is UX: the bot feels responsive, shows its work in native plan cards, stays quiet when it has nothing to add, and never spams threads.
**In v1:**
- 
A front agent that replies, reacts, sends messages on users' behalf, steers subagents, and manages memory
- 
General-purpose background subagents with Slack search, web search, URL fetch and image reading
- 
Native Slack plan cards for subagent progress, with steering and resume
- 
Per-user memory and an admin-approved workspace knowledge base
- 
Abuse controls: limits, reports, auto-suspension
**Since v1:** code sandboxes for subagents (Modal, with live previews on Cloudflare; see Code sandboxes) and admin-only coding agents that open PRs (see Coding agents).
**Scale:** a few users at first, but the architecture is built to scale horizontally from day one. Hosted at home or on a VPS.
## Stack and architecture
TypeScript on the Vercel AI SDK and Chat SDK, with models through Hack Club AI (an OpenRouter proxy), falling back to OpenRouter. Ingress and workers are separate processes from day one so the bot scales horizontally.

Ingress never calls a model, so events are always acked within Slack's 3-second window. Workers hold no per-thread state in memory: locks, inboxes and debounce timers live in Postgres and Redis, so any worker can take any thread. `fetch_url` and emoji search call the web directly.
**Per-thread event log.** Everything that happens in a thread is an append-only event: user messages (with edits and deletions), turns, spawns, steers, run progress, results and sends. The front agent's context, the plan cards, traces and eval replays are all derived from it.
**One Slack client.** Every Slack call goes through a single wrapper with per-method and per-channel rate limits (shared across workers via Redis), backoff on 429s, card-update coalescing, and idempotency keys on every side effect.
## Agent roles and tools
Three roles, each granted tools from one shared registry. Safety rules come from what each role is given, not from prompts.
- 
**Gate:** a cheap relevance check that decides whether the bot should respond to an unmentioned follow-up. No tools; outputs yes or no.
- 
**Front agent:** the only agent that talks to users. Handles one speaker per turn, replies, reacts, spawns and steers subagents, and manages memory. **One speaker** is about identity and permissions: their memories, confirmations and sends, and never steering or cancelling someone else's subagent or coding agent without its owner's go-ahead; the speaker may still ask for work a teammate requested or that helps others ("@bot ^" under a teammate's request is done). Answers directly only for trivial or quick things (from knowledge, or one or two light lookups, at most one `slack_search`; a subagent adds latency and a plan card) and delegates everything else right away, without researching first: an ask for subagents or a staged job ("step 1… step 2…") starts with `spawn_subagent`, and quick lookups that didn't clearly answer (or failed) are delegated in the same turn instead of searching on or replying "not sure". **Fan-out:** several named items that each need research (products, libraries, frameworks, people, channels, options, cities, questions) get one task each in ONE `spawn_subagent` call, also for "A vs B vs C" / "compare A, B and C" (never one "compare" task; the front agent compares on the results); one task covers a single question including its steps (find X, then compare it) or trivially small items; items that must be found first ("the top 3 X") run in rounds (one task finds the list, then one per item). The prompt, the tool description and the `tasks` field say the same (live: a three-library comparison went from one task to three). **Lookup guard** (code backstop, pure `src/agent/lookup-guard.ts`; live: a dozen web searches for a staged request, no spawn): after `limits.frontLookupNudgeSteps` (3) lookup-only steps in one front turn (research calls plus at most an ack reply / reaction / emoji lookup), a one-time `<system_note>` tells it to hand the rest to `spawn_subagent` or answer; after `limits.frontLookupRestrictSteps` (2) more, `prepareStep`'s `activeTools` drops the research tools (searches, fetches, reads, `ask_thread`, `read_canvas`, `read_file`, `ask_file`) for the rest of the turn (`lookup_guard` event). One or two lookups never reach it; subagents don't use it. Specific or current facts (named products, tools, companies, people, events, prices, anything about this workspace) are checked before answering (a search or `ask_thread`, delegated if it needs more), never answered from memory and corrected afterwards. Work is never announced without being started in the same step: an ack ("on it", "I'll update…") goes with the `spawn_subagent` / `message_subagent` or other call that does the work, or is a `reply` with `continue_turn: true` followed by the work (a reply alone ends the turn); synthesis turns too (prod: "found enough to build it…" and then nothing). **A go-ahead means act:** an explicit go-ahead to something offered or asked for ("build it", "make it", "do it", "yes", "go", a yes button) is done in that turn, without re-confirming or asking for details already in the thread, earlier turns or results; it asks only when something essential is genuinely missing (replay: "build it" and a "^" re-ping got another "want me to make…?"). A correction ("wait, I meant X") to something just done or proposed counts the same: redo it, `message_subagent` or re-propose in that turn. **Explicit format beats brevity:** the casual voice and short messages are chat defaults, not a cap; the speaker's explicit length, structure, format, tone or sourcing requirements win. Deliverables (essays, reports, quiz answers, write-ups, documents) are proper prose in the requested form, with the voice only in the short message around them, and a long one goes in a canvas or file plus a short reply (live: a 300-word explainer, a 3-part guide with 200-word minimums per part). Asked for something its tools don't support, it says so plainly, without setup questions ("which repo?").

**Parallel tool calls.** Both agents ask the provider for parallel tool calls (`parallel_tool_calls: true` in `providerOptions.openrouter`; the OpenRouter default, set explicitly, and left out for a subagent step whose tools are switched off by its token cap). The AI SDK executes all tool calls of a step concurrently once the step's model call ends. GPT-6 Luna does emit several short calls per step (checked live: four independent lookups in one step with and without the flag; with the full front prompt, a `web_search` and a `slack_search` together), but calls with long arguments (spawns, the ack reply) come one per step, hence the batched `spawn_subagent`. Both prompts tell the agents to put independent calls in one step: the front agent its ack `reply` + `spawn_subagent`, or a Slack and a web search at once; subagents several searches / fetches / `ask_thread` calls at once.

## When the bot responds
The bot always runs on a mention or DM. In threads where it has been mentioned, follow-ups pass through three layers so it replies when it is useful and stays quiet otherwise.
- 
**Deterministic rules** (pure, `src/pipeline/rules.ts` `decide`). A mention or DM always runs the front agent. A message that @mentions someone else and not the bot is skipped. Mentions count from the message body only (`mentionText`, `src/pipeline/rules.ts`): with body blocks, only their mentions (rich_text user / usergroup / broadcast elements, section and markdown text); without, the text minus any mention only a context block carries. So a footer like "Sent using @Claude" (messages sent through Claude's Slack connector, which Slack also folds into `text`) doesn't make an unaddressed follow-up `mentions_other`; attachments never count. **An answer to the bot runs without the gate:** when the bot's latest reply in the thread ended with a question (trailing `?`), an offer ("want me to…", "should i…", "if you want"…, `awaitsReply`) or quick-reply buttons, the person it was replying to (that turn's speaker) gets their next message through without the gate, whatever the idle time or engagement (it re-engages the thread), unless it @mentions someone else or starts with `<>`. Detected at reply time, not by re-parsing Slack: every delivered reply (any turn kind, also synthesis and scheduled turns) updates `threads.last_bot_reply_at` / `last_bot_reply_ts` / `last_bot_partner` / `awaits_reply_from` (migration 220); the first message that takes the flag (atomic) consumes it. **Someone else answering the bot is likely, not certain:** when the bot's latest reply awaited a person and the first human message after it comes from someone else (nobody wrote in between), it is probably taking up the question or offer too, so it goes through the gate at the partner threshold with its own code-written note (batch reason `answer_other`, pure `answersOtherOffer`; engaged threads only, the flag is not consumed, and the event logs `answersOther`). Only that first message counts.
- 
**Relevance gate.** Everything else goes to a small, fast model with the last few messages and the new one. It answers one question: is this addressed to the bot, or would the bot clearly add something? Decisions are logged for tuning. Implementation: TypeSafe's Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions API answers one typed yes/no question with a probability; ~0.45s vs ~1.2s for a chat model, 95% agreement with the earlier Luna gate on 39 logged decisions. Any Decisions API error or a 1.5s timeout falls back to the Luna chat-model gate; every `gate_decision` event logs the model, probability, threshold, partner / cooling flags and any fallback. **The threshold is contextual** (pure `gateThreshold`): `GATE_THRESHOLD` (0.8) by default; `GATE_PARTNER_THRESHOLD` (0.65; 0.5 and then 0.6 let a partner's musing to themselves through at p ≈ 0.58 / 0.62) for the bot's own conversation partner, i.e. a two-party thread (only the original poster and the bot have spoken; this used to skip the gate entirely, which made the agent treat the OP's follow-ups as optional) or the person the bot's latest reply was for, with no other human message since (batch reason `partner`), or someone else's first message after a reply that awaited an answer (`answer_other`, see above); `GATE_RECENT_PARTNER_THRESHOLD` (0.65) for the bot's latest partner when someone else wrote since the bot's reply to them, as long as that reply is at most `limits.recentPartnerMs` (10 min) old (batch reason `recent_partner`, pure `isRecentPartner`; base 0.8 dropped a partner's question after a bystander's remark at p ≈ 0.55); `GATE_COOLING_THRESHOLD` (0.9) once the thread is cooling (no address and no bot reply for `limits.gateCoolingAfterMs`, 3 h). Partner wins over recent partner, which wins over cooling. For partner batches the gate also gets a code-written note that the author is the person the bot was just talking with, so their message is most likely meant for the bot unless they're clearly just acknowledging ("ok", "nah", "got it") or thinking aloud; a recent partner gets a softer note (a question or request is probably still for the bot unless it's aimed at the other person), and the event logs `recentPartner`; the gate prompt answers "no" when unclear only while other people are talking among themselves. Prod examples this fixes: "Whats nd studio?" (p = 0.50 in prod, without the note; 0.81 with it in the live test) and "decrease polling" (0.58 → 0.94) from the bot's conversation partner.
- 
**Front agent.** On yes, the front agent runs and can still choose silence by not calling `reply`. Turns from an answer to the bot or a partner follow-up that passed the gate are stored as `turns.addressed` and framed as "<@speaker> is talking with you in this thread (no @mention needed): respond"; when it came through the gate (a partner or `answer_other` batch, not a direct answer to the bot's question) the framing adds "unless they're clearly just acknowledging or thinking aloud". A `recent_partner` pass is a `turns.gated` turn, not addressed. Every other batch that passed the gate is stored as `turns.gated` (migration 240) and framed as "a relevance check judged this is meant for you (or that you clearly have something to add): respond unless it is clearly not for you": the agent no longer second-guesses a gate yes (prod: a p = 0.92 pass ended silently under the old wording). The cautious unmentioned-follow-up wording ("respond only if it is addressed to you…; otherwise do nothing") is left only for a user turn that is neither a mention, addressed nor gated; no path creates one today (messages pushed into a running turn's inbox are framed as "sent while you were working", and leftovers it never drained go back through the gate), so it only covers turns queued before migration 240. Gated turns don't get activity cards (unchanged).
**Never triggered by bots.** Messages from bots (`bot_id` or `subtype: bot_message`), including the bot's own and its on-behalf-of messages, never start a turn. Bot messages are still included in context, labelled as bots.
**Intake hygiene.** Slackbot's system messages (`USLACKBOT`, e.g. "you were added to a user group" in the bot's read-only DM with Slackbot) are ignored at intake entirely: not stored, no thread, no turn. A DM whose other party is a bot or an app user (`users.info` `is_bot` / `is_app_user` of the DM's author, cached per DM channel for a week in Redis, `src/pipeline/dm-peer.ts`; a failed lookup fails open) never starts anything. When any Slack call fails with `restricted_action_read_only_channel`, the shared client marks that channel read-only for a day (Redis, `src/core/slack.ts`), and intake starts no turns there meanwhile (the message is still stored as context).
**Disengagement.** A few idle hours only cool a thread (the stricter gate above). The bot stops considering follow-ups until mentioned again after more than 25 unaddressed human messages (`limits.disengageAfterMessages`) or 7 days without being addressed and without a reply of its own (`limits.disengageAfterMs`; any bot reply, including synthesis and scheduled turns, restarts the idle clock). "Shut up" / "go away" make the agent call `leave_thread`, which also disengages it (and clears an awaited answer).
**Workspace AI-bot guidelines** (enforced in code: pure checks in `src/pipeline/guidelines.ts`, side effects in `src/pipeline/guideline-actions.ts`; they apply in channels, threads and DMs and run before the rules above):
- 
`##` **prefix: ignored completely.** A message whose trimmed text starts with `##` (mention or not) is never stored, adds no thread events, never triggers a turn, the gate or a debounce batch, and doesn't count toward limits or disengagement. It is also hidden from everything the bot reads: thread/channel backfill, `read_thread`/`read_channel` and `slack_search` results. Editing a message to start with `##` is treated like deleting it (stored copy blanked, dropped from batches and pending turns). Editing the `##` away never triggers a turn; a copy that was blanked stays blank, a never-stored one may be stored as plain context.
- 
`@bot !stop` **= stop the current response** (anyone may use it). A message mentioning the bot whose remaining text is `!stop` (case-insensitive) runs the stop handler (`src/pipeline/stop.ts`) for its thread: abort the running turn mid-step, drop the user's pending turns/inbox/batch, set the session `active`, post "Stopped." (the thread stays engaged and subagents keep running; asking in text cancels them). It never starts a turn itself. In DMs the mention is optional. At a channel's top level it applies to that message's own (empty) thread, so it's harmless. **Mid-step abort:** the front turn polls the stop flag every 500 ms (`STOP_POLL_MS`) and aborts an AbortController passed to `streamText` and, as `ctx.abortSignal`, to every tool; `toolsFor` (`src/core/tools.ts`) wraps each tool so none starts once the turn's signal (or the call's own) has fired (`STOPPED_TOOL_RESULT`), since the AI SDK may still dispatch a call it parsed just before the abort (prod: a `create_canvas` still being written ran after "Stopped."). A reply cut off mid-stream is closed keeping what was shown and recorded as a stopped reply (`closeStopped`).
- 
**Group ping on a top-level trigger → answer elsewhere.** When the message that triggers the bot is a top-level channel message that pings a user group (`<!subteam^…>`) or `@channel`/`@here`/`@everyone`, the bot doesn't reply under it. It posts a new top-level message ("<@user> asked me something in <this message>, replying here so the group thread stays clean", idempotent on the source ts, no group ping), stores the user's message as part of that new thread, and runs the turn there (replies, cards and status included). Follow-ups in the new thread work normally (the asker counts as the thread's original poster for the two-party rule); the group-ping thread is never engaged. Thread replies and DMs with group pings are answered in place.
- 
`<>` **prefix: don't reply unless mentioned.** A message whose trimmed raw text starts with a literal `<>` (Slack delivers it as `&lt;&gt;`) never triggers a turn or the gate unless it @mentions the bot, in which case it's a normal mention. It is still stored and visible as context. DMs included.
- 
**The bot never pings groups.** `reply` text (also while streaming) and card fallback text have `<!channel>`, `<!here>`, `<!everyone>`, `<!subteam^…>` and plain `@here`/`@channel`/`@everyone` neutralised; `send_message` already did this.
**No native stop button.** The user found Slack's stop button too easy to click by accident, and the only way to remove it is not subscribing to `agent_session_stopped` (removed from `slack-manifest.yml`). Users then see a non-interactive loading indicator, and `agents.sessions.setStatus` (and the streaming calls) answer with a `missing_agent_session_stopped_event_subscription` warning, which the shared Slack client's logger drops to debug (`QUIET_SLACK_WARNINGS` in `src/core/slack.ts`). `@bot !stop` is the way to stop a response; the `agent_session_stopped` handler stays (it is what `!stop` runs). A stream Slack halted (`stopped_by_user`, `not_in_streaming_state`, …) is never rewritten (`HALTED_STREAM`, `src/agent/reply.ts`).
**Status indicator.** The agent session's lifecycle via `agents.sessions.setStatus`: `processing` (Slack's "Working…") and `active` when the turn ends, always (also on errors). Mentions and DMs show it as soon as the message is accepted at intake, before the debounce window; the turn takes it over, and it is cleared if no turn follows. Status calls never delay the model call. Unmentioned follow-ups show it only once the turn commits to work — its first tool call other than `reply`/`react`/`unreact`/`search_emojis` (and the bookkeeping `leave_thread`); a turn that stays silent or goes straight to `reply` never shows a status (the streamed reply is its own indicator) and gets no acknowledgement reaction. A reply stream that ends mid-turn sets the session `active` (`chat.stopStream`'s default), so the next tool call sets `processing` again — except bookkeeping after the reply (remember/forget, workspace facts, reminders/watches), which leaves the indicator alone. A turn the user stopped never sets `processing` again. **Activity text** ("Searching Slack…", "Reading the page…", "Starting a subagent…", code-derived from the tool being started; "Searching the web…" for web search): the deprecated `assistant.threads.setStatus` (the only free-text status, removed with `assistant_view` in February 2027) is no longer used, and `agents.sessions.setStatus` takes no custom text. Instead (`STATUS_ACTIVITY_MODE=tasks`, default) the activity is the live plan of the turn's reply message (`src/agent/activity-trail.ts`): the first activity opens a stream in plan mode (`task_display_mode: plan`, a `plan_update` titled "Working…"; timeline task cards if Slack refuses plan mode) holding one `task_update` task, later ones add tasks (at most one update per second, latest wins, unchanged text skipped). Tasks are tied to their tool calls: a task completes when its calls return (`error` only when a call threw), a tool that returns before its task went out shows none, and a task without a tracked call completes when the next one replaces it. **No task is ever left `in_progress` when its stream stops:** Slack renders such a task as failed (a ⚠ icon, until the delete lands), so adoption and every `chat.stopStream` carry the chunks that finish all open tasks (a stop Slack refuses with chunks is retried plainly before the delete). The turn's next reply adopts the message: a streamed reply streams in below the plan; a reply posted whole (subagents running) is written into it (`chat.stopStream` with every task finished, then `chat.update` [card, reply, buttons]), and if the message can't take it, it is deleted before the post and no new activity message opens while the post goes out. The final layout (`chat.update`, retried briefly on `streaming_state_conflict`) replaces the live plan with the turn's plan card rendered from the DB (see Plan cards), or no card for a turn without lookups or runs. A turn that never replied (silent, error, stop) deletes its activity message, so nothing is left behind. A reply doesn't adopt the activity message when anything was posted in the thread after it (it would land above that post) or when Slack already ended its stream (only a confirmed user stop drops the reply): the activity message is deleted and the reply opens its own. Cards only show in turns that are expected to reply (DMs, mentions, reminder turns, subagent write-ups) and only until the turn's reply is visible; unmentioned follow-ups get just the lifecycle status (a card posted and deleted in a channel thread can notify its followers). A worker crash or shutdown mid-turn leaves none behind: the open activity message is recorded per turn in Redis, and the stale-turn sweep / shutdown deletes it and sets the session's final status. If Slack refuses a cards-only stream, the turn just shows "Working…". `STATUS_ACTIVITY_MODE=off`: "Working…" only. In DMs the session also gets a title and richer statuses (see Agent sessions in DMs).
## Turns
Every front-agent turn has exactly one speaker, and only one front agent runs per thread at a time. This keeps "current speaker" well defined for memory, tools and steering.
**Debounce per (thread, author).** Messages from the same person within the window merge into one turn; messages from different people never merge. The window scales: about 300 ms for DMs, mentions, answers to the bot and partner follow-ups (two-party threads, the bot's latest or recent conversation partner), about 1 second for other gated messages, 3 seconds while the thread has running subagents. It is re-evaluated as each message arrives. A same-author message that misses the short window still reaches the running turn through its inbox (or starts the next turn once the reply is out).
- 
An edit during the window replaces the message in the batch. Only a real change counts as an edit: `message_changed` whose text and files equal the stored copy (Slack re-sends a thread root unchanged every time a reply is added) updates nothing and logs no `message_edited` event. Previous texts are not stored.
- 
A deletion during the window removes it; if that empties the batch, the turn is cancelled.
**Sequential turns.** If two people message at once, their turns run one after the other. The second turn sees the first turn's messages and reply as ordinary thread context.
**Messages arriving while a turn runs:**
- 
The message goes through its debounce window first.
- 
If no turn is running, a new turn starts.
- 
If the running turn belongs to the same author and has a tool boundary coming, the message is pushed to the thread inbox and injected before the next model call.
- 
If the running turn is in its final reply (no more tool calls), or belongs to a different author, the message waits and starts a new turn right after.
- 
Messages pushed into a running turn's inbox skip the gate (the turn sees them before its next step). Ones it never drained (it ended first) are leftovers: if they all needed the gate (inbox rows keep their intake reason, migration 220), they go back into the author's debounce batch and through the gate like any other message (`inbox_regated` event); a mention, DM, button press or answer to the bot among them makes them a new pending turn as before.
- 
A user turn that follows a turn which used tools (finished within `limits.previousTurnToolsMaxAgeMs`, 30 min) gets `<previous_turn_tools>`: the previous turn's tool calls, one line each (tool + JSON args, clipped to 200 chars, at most 12; replies, reactions, emoji lookups and `end_turn` left out), from the `turn_tools` event the front agent writes at the end of every turn. Calls only, never results (no Slack content), so "yes, make it" knows what was looked up instead of asking again.
**Results / scheduled turns wait for pending messages** (`src/pipeline/turn-hold.ts`, pure `decideHold` / `yieldCutoff` / `pickNextTurn`; state in Redis, `claimNextTurn` in `src/pipeline/scheduler.ts`). A synthesis or scheduled turn that comes up while someone's newer message in the same thread is still in its debounce window or at the relevance gate waits for it, up to `limits.turnHoldMaxMs` (8 s): the thread-run holder releases the thread lock and re-checks via a delayed thread-run job every `limits.turnHoldPollMs` (1 s); the debounce fire wakes the thread as soon as it has scheduled or dropped the batch. A taken batch is marked in flight atomically with the take (the gate's marker expires after `limits.gateInflightTtlMs`, 30 s, if a worker dies mid-gate). When the turn stops waiting it fixes a yield cutoff: user turns already queued behind it run first (they answer with their speaker's own tools, e.g. the admin's `spawn_coding_agent`); later user turns wait behind it, so it is never starved. A user turn that runs ahead of waiting results is told the results get written up right after it (`resultsAheadNote`: don't report, guess at or redo them). Events: `turn_held`, `turn_hold_ended` (`waitedMs`, `timedOut`), `turn_yielded`. Without the hold, a results turn saw the message in `<thread_history>` and answered or refused it, and the message's own turn answered again. **Fallback note:** the turn instruction of a non-user turn still lists the user turns already queued ("Queued after this turn …") and the human messages stored after the bot's last reply (`threads.last_bot_reply_ts`, within the last 15 minutes, at most 10) that no turn or inbox row has taken ("Still being handled: … they get a turn of their own if they're meant for you, so don't answer, refuse or act on them here"; `renderQueuedTurns` in `src/agent/front.ts`), which covers a hold that timed out and a message the gate later drops.
Apart from `@bot !stop` (which aborts the running turn mid-step, see above), turns are never hard-interrupted: "stop" in a normal message is injected like any other message, and the agent responds by cancelling subagents and staying quiet.

Subagents are persistent sessions within a thread; each piece of work on one is a run. Steering a running subagent and following up on a finished one are the same operation.

**Front agent tools:**
- 
`spawn_subagent(tasks: [{ title, instructions, seed_from? }])` creates one subagent per task (up to 6, each checked against the limits; a task that can't start is reported back without failing the others) and starts their first runs, all on the turn's plan card. Batching is in the schema because GPT-6 Luna, given the full front prompt, emits long-argument calls like spawns one per step even with parallel tool calls on (checked live: three spawns took three model steps; with the `tasks` array it is one call).
- 
`message_subagent(id, text)`: if running, pushes to its inbox; if idle, starts a new run on the same session with full prior history; if cancelled, errors so the agent spawns a new one.
- 
`cancel_subagent(id)` sets a flag; the run's heartbeat (every `limits.heartbeatMs`, 10 s) sees it and aborts the run mid-step (the model call and the tools in flight; tools refuse to start once aborted), and the run ends `cancelled`.
**Inbox and steering.** Each subagent loop drains its inbox before every model call and appends messages as `[Orchestrator update] …`. Injection only happens at turn boundaries, never mid tool call.
**Ownership.** Each subagent records the user who spawned it. The front agent sees message authors and subagent owners, and is prompted not to steer or cancel another user's subagent without the owner's confirmation. This is prompt-only, not enforced in code.
**Results.** Subagents never talk to users. Their results go back to the front agent, which writes the answer in its own voice. Failed and cancelled runs are reported in the synthesis, not dropped. The synthesis turn instruction (`SYNTHESIS_INSTRUCTION` in `src/agent/front.ts`, only in synthesis turns) has it decide: (1) **a focused next round** when the round was only a first step of what was asked, or more research could fill gaps the request needs (a part unanswered or thin, leads the results name but didn't follow, contradictions, a list of things to dig into): new subagents (parallel when independent) and/or `message_subagent`, passing on the leads and what's known, with a short reply in the same step; not when a deadline the speaker set (vs `<current_time>`) leaves no time, or when the last round (`<earlier_rounds>`) already chased these gaps and added nothing; (2) **produce the deliverable** when the results were groundwork for something the speaker asked to be produced (a file, page, canvas, message, or a next step): in that turn (or start the round that does), not a report plus an offer to make it (replay: a results turn listed the projects found and offered to build the page it had been asked for); (3) otherwise **answer**: the best-supported answer to every part of the request, also from partial evidence, hedged per claim ("likely", "per one message from kai in <#C123>", with a link) and keeping the subagents' doubts; "not found" only for a part with no evidence at all; never refusing the whole task, replacing answers with a note on what's missing, or inventing what no source says. **Requested length, structure and format are requirements** (e.g. "at least 250 words per part", numbered parts, a source per fact): met in full, for thin parts too, with substance from the results, not padding; otherwise it leads with the answer and keeps it tight. A document to keep goes in a canvas (`create_canvas(from_subagent)` for a subagent's full result), files the runs made go out with `reply(files)`.
**Research method** (child prompt, `src/agent/prompts/child.ts`). Search hits are pointers, not answers: open the most promising threads (`ask_thread` with a specific question; `read_thread` / `read_public_thread` for exact messages) and read what people actually said. Every new name, nickname, codename, project, repo, channel, bot, emoji or link is a lead: search for it in Slack, and look up projects and repos on the web or GitHub; connect clues; at a dead end change angle (other terms, the people involved, sort "oldest" for where it started). Usually a few `slack_search` calls per step (it's shared and rate limited), then open the best hits before searching more. Keep going while strong leads are unexplored; stop when the task is answered or the leads run out, not after a set number of searches. Check what each message is actually about (a thread reply needs its thread; the parent, forwarded content, the channel's purpose) and never attribute a date, place or fact to the wrong event, project or person. The final message answers every part with the best-supported answer marked by confidence ("confirmed", "likely", "one mention"), a quote and permalink per key fact and no guessed gaps, then lists what wasn't found and the leads not followed, and ends with a `SUMMARY:` line. A LIVE test with invented data (`src/agent/research-depth.live.test.ts`) covers a multi-hop codename lead across two threads and synthesis with partial results (a deadline → per-part answers; time left + an unfollowed lead → a focused next round).
**History.** Subagent history is persisted (Postgres). When a run ends, old tool results are compacted to summaries so long-lived subagents don't grow without bound.
**Front agent snapshot.** Every turn includes a list of the thread's subagents, running and idle, with owner, status and a one-line summary, so the agent can reuse an idle subagent instead of starting from scratch.
**Expiry.** Idle subagents expire after about 24 hours and drop out of the snapshot. A later follow-up spawns a fresh one, seeded with the old summary.
**Deploys and crashes.** Workers heartbeat while running. A sweeper marks runs with stale heartbeats as errored and updates their cards. On shutdown, in-flight runs are marked errored before exit. Runs are not resumed after a restart.
## Slack UX
Everything the user sees is produced through tools, and code decides how it's delivered.
### Reply tool and delivery
- 
`reply(text, files?)` posts in the current thread. Not calling it is a valid choice: a steer often needs only a reaction and a card note.
- 
Multiple `reply` calls per turn are allowed (for example, one before spawning, one after), but most turns have one or none.
- 
**A reply or reaction ends the turn.** The loop stops after a step whose `reply` / `react` / `unreact` actually went out (posted, reacted, removed; not an empty, skipped or stopped one) when every other call in that step is terminal-safe, i.e. its result isn't needed to go on: `spawn_subagent`, `message_subagent`, `cancel_subagent`, `spawn_coding_agent`, `remember`, `forget`, `propose_workspace_fact`, `leave_thread`, `send_message`, `report_user`, `end_turn`, `set_reminder` / `cancel_reminder`, `create_watch` / `cancel_watch`, `huddle_dj_settings` (and only when they returned a result: a failed spawn reaches the model). Searches, fetches, reads, `ask_thread`, canvases, `list_*`, `search_emojis` and the DJ commands keep the turn going so the model sees their results. The list and the rule are pure and tested in `src/agent/turn-end.ts`; the same rule sets the turn's phase to `final`. All three tools take `continue_turn: boolean` (default false) to keep working after an ack. `end_turn` remains for silent turns. Before this, every turn spent an extra model step (~1.9 s in prod) just to call `end_turn`.
- 
If a turn ends with no reply, no reaction, no card change and no spawn, fall back to posting a short message so the user isn't left with silence.
- 
Reply text is markdown, delivered exactly as the model wrote it (`src/agent/slack-markdown.ts`): prose as `markdown` blocks, fenced code as `rich_text` blocks with a `rich_text_preformatted` element (always with a `language`, else Slack drops the rich code component). Reason: Slack's markdown converter rewrites `<h1-6>`, `<code>` and `<img>` into markdown everywhere, even inside code (verified); in prose only those tags' `<` is written as `&lt;`, and a paragraph whose inline code contains one is rendered as `rich_text`. Streams run in `chunks` mode: prose as `markdown_text` chunks, each code block held until its fence closes and sent as a `blocks` chunk; a stream that carried blocks is re-rendered with `chat.update` after `stopStream` so its final layout equals the posted one. No other rewriting of model output (no citation-marker stripping) except one: a single-star `*x*` on one line (not `**`, a `* ` bullet, inside a word like `2*3*4`, escaped, or in a code span) is sent as `**x**` (`boldSingleStars`). The prompt asks for **bold** and _italic_, but the model often writes Slack mrkdwn's `*bold*`, which Slack's markdown block renders as italic; rich_text rendering agrees (`*x*` bold, `_x_` italic), and streaming holds back an unclosed opener or a trailing star so what was sent never changes. Group pings are still neutralised.

### Quick-reply buttons
- 
`reply(text, files?, buttons?)`: `buttons` is an optional list of 1–5 short labels (≤ 30 chars asked for in the description; shown as written: code only neutralises group pings, drops empty labels, cuts at Slack's 75-char button limit and keeps at most 5; the schema stays lenient so a violation can't fail a reply whose text already streamed). The prompt asks for them only when the reply ends with a question with a few clear answers; each label is exactly what the user would reply.
- 
Rendering: an `actions` block (`block_id` `reply_<id>_buttons`, `action_id` `reply:choice:<i>`, `value` = `reply_buttons.id`) right under the reply markdown. Posted replies include it directly. Streamed replies pass it as `blocks` to `chat.stopStream` (documented: "A list of blocks that will be rendered at the bottom of the finalized message"; separate 50-block limit). If that is refused, the stream is stopped plainly and the buttons are added with `chat.update`; if that fails too, they are posted as a small follow-up message (logged).
- 
State lives in `reply_buttons` (labels, message ts + text, presser, pressed label, the press's message ts). A plan card attached to the same reply re-renders [card, reply, buttons or pressed note] from the DB.
- 
Press (`reply:choice`): entry guard (counted as a message; blocked users get nothing, rate-limited ones an ephemeral); the first press is claimed atomically (`pressed_at is null`), later presses get an ephemeral "already answered". The buttons are replaced by a context block "<@presser> pressed *label*" (`chat.update`, through the card renderer when a card lives there). Then it acts as if the presser replied with the label: a synthetic message (ts = the action's `action_ts`) is stored, a `message` event appended, the thread marked addressed/engaged, and a mention turn scheduled for the presser (inbox push into their running turn, or a pending turn). The presser is the turn's speaker.
- 
Context: the bot's reply shows `[buttons: A | B]` (`[buttons: A | B; Ingo pressed "B"]` once pressed) and the press renders as `<@U> Ingo: B (button)`.
### Answers to button clicks
Ephemeral answers to a click (`ephemeral()`, `src/features/util.ts`) land in the clicked message's thread: a click in a thread is answered with `chat.postEphemeral` (channel, user, `thread_ts`), because `response_url` posts (new ephemerals, and replacements of an ephemeral message) land at the channel / DM root (prod: the claim link, "Thanks. Deploying…", "Cancelled."). `replace` there removes an ephemeral source message (`delete_original`) and posts the text in the thread; a regular message is still replaced in place. Ephemeral buttons carry no thread, so the send, coding-agent launch and preview handlers fill it from their row (`withThread` / `threadTs`). A click on a thread's parent, and clicks outside threads, use `response_url` (else `chat.postEphemeral`) as before.
### Plan cards
-
**One plan card per bot message** (`src/agent/turn-card.ts`, `src/agent/cards.ts`, pure rendering in `src/agent/card-render.ts`). A turn's card holds its own steps (`cards.steps`, migration 260, in call order; `src/agent/card-steps.ts`: web and Slack searches, page fetches, thread / channel / canvas / file reads (`ask_thread` and `ask_file` count as reads), file and canvas writes; not bookkeeping, responses or the subagent tools) and the runs it started (one task row per run, only runs started in that turn). Steps are recorded only where activity cards show (mentions, DMs, write-ups), so unmentioned follow-ups stay card-free; a turn with no step and no run has no card.
-
**Where it lives:** the turn's reply message, laid out [card, reply, buttons / pressed note]. While the turn works, its steps show as the activity stream's live plan (see Status indicator); the reply that goes out carries the card rendered from the DB (`cardBlockFor`; `attachCard` records `message_ts` + `reply_text`), and at the end of the turn `TurnCard.finish` saves the final steps (a step still running then counts as done: it never failed) and re-renders the card in that message, or attaches it to the turn's last reply (`chat.update`). If that update fails, a card with runs is posted as its own message and a `card_attach_failed` event + warning (with the Slack error code) is logged; a steps-only card is never posted alone. A turn with runs but no reply posts the card alone. Every re-render rewrites [card, reply, buttons] from the DB; card updates retry `streaming_state_conflict` briefly.
-
**Finished cards.** A card is finished once nothing on it is in progress (no step running, no run queued or running) or it was frozen after its synthesis write-up. It stays the same Slack `plan` block (`block_id` `card_<id>_plan`, one plan per message, above the reply) with every task final: the turn's steps (`complete`/`error`; a step still marked running when the turn ended counts as complete) and each subagent run (`complete` with its summary in bold, a result excerpt and up to 5 sources, or `error` with the error / "Cancelled", duration in the task title). Slack shows a plan block collapsed to its title by default and expands it on click (observed in the Slack client; not documented), so there is no collapsing logic of our own. Title: live "Running N subagents" ("Working…" while only a step runs); finished, the background card title (titles queue, after the synthesis, e.g. "Compared 3 hosting options"), until then a summary ("Searched Slack, read 2 pages, ran 3 subagents (1 failed)"), else "Ran N subagents"; clipped to 150 characters, group pings neutralised. A turn without steps or runs has no card.
-
**Multi-round:** a synthesis turn that starts another round gets a card of its own in its write-up message (`cards.parent_card_id`, migration 100, points at the card whose results led to it); the earlier round's card is frozen in its own message. Synthesis turns see the chain's results as `<earlier_rounds>` (up to 4 rounds back, older rounds with a smaller budget).
- 
Steering a running subagent does not create a card. The steer appears on the original card's row as `↪ also checking #ship`.
- 
Resuming an idle subagent is a new run, so it appears on the new turn's card, marked `↻`.
- 
Task rows show results, not just a one-liner: a finished run's `output` is its summary in bold plus a markdown→rich_text excerpt of `runs.result` (≤ 600 chars / 8 lines with ≤ 3 runs, 300/4 with ≤ 6, 150/2 with ≤ 12, summary only beyond); failed runs show the reason, cancelled ones "Cancelled". `sources` lists the URLs the run used (`runs.sources`: fetch_url targets and web-search result URLs, tracking params stripped, deduped; falls back to URLs in the result text), up to 5 (fewer with more runs). Slack documents a 50-task limit per plan (enforced: latest 50) and 50 blocks per message; no per-task output limit is documented.
- 
Cards are updated with `chat.update`, never a held-open stream. The message is a pure render of task state from the DB; children write progress to the DB and schedule a re-render.
- 
Updates are coalesced per card to at most one every `limits.cardCoalesceMs` (1.5 s; a Redis flag + delayed `card-render` job, a per-card lock so two workers never apply updates out of order), always rendering the full latest state. Always set `text` alongside `blocks`.

### Reactions and emoji
- 
`react(emoji)` takes any emoji name. The model is prompted on when to react, and that steers should get a visible acknowledgement nearby (a reaction or short reply), since the original card may be far up the thread.
- 
`search_emojis(query)` is backed by semoji (`/v1/search`, hybrid mode), returning name and summary for about 8 results. Results are cached; timeout ~1s.
- 
If a lookup fails or `reactions.add` returns `invalid_name`, fall back to `thumbsup` or skip silently.
### Files
**File store** (`src/files/`, migration `230_files.sql`). Global storage, thread-scoped access. One `files` table holds every file the bot made (`origin = created`) and every Slack upload it has shown a model (`origin = upload`, one row per thread the upload appears in). Ids are `file_` + 10 random lowercase alphanumerics (e.g. `file_k3x9q2mf7a`; unique, re-drawn on collision). Columns: origin, thread and channel, owner (the uploader, or the speaker the bot made it for; subagents make files for their owner), what created it (turn or run + subagent), the Slack file id / `url_private` / message ts (uploads), name (sanitised: no directories, control characters or leading dots, ≤ 120 chars), MIME type (sniffed from the content first, then the extension), size, sha256, a description and its source, an `internal` flag (never usable through tools; for the sandbox's preview bundles), the content (bytea, ≤ `limits.fileMaxBytes` = 5 MB) and `legacy_image_n`. Content sits behind a small `FileStore` interface (`put` / `get` / `getRange` / `metadata` / `delete`, `PgFileStore` today) so it can move to object storage later. The sandbox (see Code sandboxes) plugs in here: `sandbox_export` = `createFile({ …, createdRunId, createdSubagentId, idempotencyKey, maxBytes })`, `sandbox_import` = `resolveFile(id, { threadId, speakerId })` + `loadFileBytes(meta, { maxBytes })`, preview bundles = `internal: true`. Only those pass a larger `maxBytes` (25 MB exports and bundles, 50 MB imports, the latter not stored); everything else keeps 5 MB.

**Access rule** (one pure function, `src/files/access.ts` `canUseFile`, unit-tested): a turn or run may use a file when it was created or uploaded in that thread, or the bot posted it into that thread, or the current speaker is its owner. So "post the page you made me yesterday in #general" works for its owner, but a file from someone else's DM can't be pulled into a public channel by guessing an id. Subagents act with their owner as speaker, in their thread. Every model-given id goes through `resolveFile`, which answers "no such file here" for both unknown and forbidden ids (ids can't be probed); migrated `img_N` ids still resolve in their own thread.

**Uploads become file ids.** When messages are rendered for a model (thread context, inbox messages, `read_thread` / `read_channel`), their Slack files are registered (`registerSlackFiles`, idempotent and race-safe per thread + Slack file): metadata only, including Slack's size. The context line is `[file file_k3x9q2mf7a: screenshot.png, image, from Ingo — "Grafana panel, p99 spikes at 14:02"]` (kind: image, html, text, pdf, audio, video, archive, binary; the description appears once one exists). The content is downloaded lazily on first use with the bot token (`src/files/slack-download.ts`: only to files.slack.com, through safeFetch) and stored when ≤ 5 MB; bigger images (≤ 25 MB) are still viewable (only the resized image is cached), other bigger files are refused before downloading. Files on `##` messages are never registered (those messages are never stored or rendered); files on other threads' or channels' messages read through the public tools (`read_public_thread`, `read_public_channel`, `ask_thread` on a permalink) stay plain `[file: name]` placeholders. A Slack file that is the bot's own post of a stored file (`file_posts`) maps back to that file's id.

**Tools** (front + children, `src/files/tools.ts`):
- `create_file(name, content, description, encoding?)`: UTF-8 text, or `base64` for small binaries; ≤ 5 MB; ≤ 20 per turn / run; idempotent per turn / run + name + content. Returns the id and metadata. The creator's one-line description is stored with it.
- `read_file(file_id, offset?)`: text files come in pages of `limits.fileReadPageChars` (24k chars, cut at a line break) with a header like `[chars 0–24000 of 81234; next: read_file file_id=file_… offset=24000]`, wrapped as untrusted content. Images go into the model's context exactly as `read_image` did (download, resize to ~1500 px, HEIC → JPEG, GIF first frame, disk cache by Slack file id; a tool-result image part, or the `queueUserImage` fallback). PDFs, audio, video, archives and other binaries return metadata only. It replaced `read_image`.
- `ask_file(file_id, question)`: a separate model call (children's model and settings, like `ask_thread`, no tools, 90 s timeout, usage recorded against the speaker / subagent owner) answers one question from one file: images as a vision call, text capped at `limits.askFileMaxTokens` (~60k tokens; the head, with a note). The answer comes back as untrusted content. At most 12 calls per turn / run, so batches work (ten screenshots → ten parallel `ask_file` calls).
- The prompts: look at an image with `read_file` when the image is the point, `ask_file` when only facts are needed or for batches; pass relevant file ids to subagents; post subagent-made files with `reply(files)` without reading them; HTML files are fine for "build me a page" (Slack renders them).

**Descriptions** are one line, ≤ ~200 chars, sanitised (no control characters, quotes softened, brackets and angle brackets neutralised so they can't break a placeholder) and treated as untrusted. Created files: the creator's. Uploads: generated on the first `read_file` / `ask_file` of the file by a cheap background call (the gate's model settings, reasoning off, ~120 output tokens; images as a vision call, text from the first 8k chars; one per file across workers via a Redis claim), stored, and shown in every later context line. It never blocks the turn.

**Posting.** `reply(files)` takes file ids (uploads from this conversation, subagent results, `create_file`, the speaker's own files from elsewhere) or an inline text file `{filename, content, description?}`, which is stored as a created file first, so one step still suffices for a quick snippet file. Unknown or forbidden ids are reported in the tool result (the schema stays lenient: the reply text may already be streaming). At most 10 per message. Files are uploaded with Slack's external flow via `slackCall` (`files.getUploadURLExternal` → POST → `files.completeUploadExternal` into the thread, idempotent per reply of a turn); when a reply is streamed they go up after `stopStream` so they land just below it. Each posted copy is recorded in `file_posts` (Slack file id → file id, thread): its message maps back to the same id, and the file becomes usable in that thread. `send_message(files)` takes the same ids / inline files; the pending send stores the ids and uploads them at Send.

**Subagent results** list the files each run created by metadata only (`file_…: page.html (html, 4.2 KB) — "description"`; `filesCreatedByRuns`, internal files excluded), in the synthesis turn's results and in `<earlier_rounds>`. The front agent can post them with `reply(files)` without reading them.

**Retention.** Created files: 30 days after creation (`limits.createdFileRetentionMs`). Uploads: with the normal message retention (30 days), and right away when their Slack message is deleted or the file is removed from it (`message_changed` with a tombstone file; `removeMessageFiles` from the pipeline's delete / edit handling, plus a daily sweep for stragglers); their post mappings go with them. The resized-image disk cache is pruned weekly.

**Migration from img_N.** Before the file store, images had per-thread ids `img_N` (`thread_images`, `threads.next_image_n`). Migration 230 moves every `thread_images` row into `files` as an upload (same thread, Slack file id, URL, uploader, message ts, name, MIME type, `legacy_image_n = N`), then drops the table and the column. Old subagent histories and run instructions that say `img_3` keep working: `read_file` / `ask_file` resolve `img_N` through `legacy_image_n` in that thread only.
### Canvases and artifacts
Long-form deliverables (research write-ups, guides, plans, comparison tables) go into a Slack canvas instead of a wall of text: the front agent calls `create_canvas(title, content)` and replies with a short summary plus the link. Subagents only read canvases; for long deliverables they return the full markdown and the front agent publishes it with `create_canvas(from_subagent)`, which copies the stored `runs.result` server-side (the front agent's synthesis view is clipped, and re-emitting a whole document as tool args is slow and lossy). Code, scripts and HTML prototypes are attached as files through `reply(files)` (any text file; Slack picks the type from the extension).
- 
**read_canvas(canvas, offset?)** (front + children): link (`https://<ws>.slack.com/docs/T…/F…`, also `app.slack.com/docs/…` and `/files/U…/F…` permalinks) or `F…` id. Fail closed, allowed only when: the bot created it in this conversation or in a verified public channel (not "anywhere for its creator": a canvas made in a private channel, group DM or DM may hold others' private messages or the creator's memories); or it is shared in / linked to the current conversation; or it is shared in / linked to a channel verified public via cached `conversations.info` (same check as Slack search). Where it is shared comes from `files.info` with the bot token (`channels`, `groups`, `ims`, `shares`, `linked_channel_id`), so canvases the bot can't see are refused. Content from `canvases.getContent` (markdown; canvas mentions `![](@U…)` turned back into `<@U…>`), wrapped as untrusted together with the title (both are author-controlled), 24k chars per call with `offset` paging. Counted against an hourly per-user limit.
- 
**create_canvas(title, content?, from_subagent?)** (front only): `canvases.create` (standalone, owned by the bot) with the markdown converted to canvas syntax (`<@U…>` → `![](@U…)`, `<#C…>` → `![](#C…)`, `<url|text>` → `[text](url)`) and group pings neutralised (also the canvas forms). Access via `canvases.access.set`: the current channel gets read (`channel_ids`), a group DM's members get read by user id (channel ids are invalid there), the speaker gets write. If `conversations.info` fails, the kind isn't guessed: the channel grant is tried, then member ids. Whenever the conversation's grant fails, the tool result tells the agent that others may have to request access (also when the speaker's grant worked). `from_subagent: "sa_…"` (also on `edit_canvas` append / replace_section / replace_all) takes the document from that subagent's latest complete run instead of `content`, which becomes an optional short intro (≤ 3000 chars): only subagents of the current thread, same conversion and ping neutralisation, cut at the write cap (100k chars) with a note. Synthesis turns' clipped results point at it. Recorded in `bot_canvases` (canvas, channel, thread, creator = speaker, turn, title, link). Idempotent per turn + title/content hash (DB row + Slack idempotency key), so a retried turn or a repeated call returns the same canvas. The tool leaves showing the link to the reply; a turn that created a canvas but posted no reply posts the link itself (from `bot_canvases.turn_id`) instead of the generic "couldn't come up with a reply" fallback.
- 
**edit_canvas(canvas, action, …)** (front only): only canvases in `bot_canvases`, and only when the speaker is their creator (the person who asked for them; others in the same channel can read but not edit it), so the bot can't be steered into editing anyone else's canvas. `append` (`insert_at_end`), `replace_all` (`replace` without section), `rename` (`title_content`), and `replace_section(heading, content)`: the canvas markdown is read, everything under the matching heading (up to the next heading of the same or higher level) is replaced, and the result is written back with `replace` (the whole document is converted and its group pings neutralised again, since the bot re-posts all of it; edits people make at the same moment can be lost, so the tool description prefers `append`). `canvases.sections.lookup` isn't used: a section id names a single block (a heading is its own section) and lookup can't list the blocks under a heading. Idempotent per turn + input hash. A canvas that no longer exists drops its row.
- 
Channel canvases (`conversations.canvases.create`) are not used: they change a channel's tab for everyone and a channel has only one.
- 
**Artifacts.** Slack Code (2026) shows agent "artifacts" (code diffs, Block Kit views, HTML previews, canvases) in code channels, but there is no documented public API for apps to publish them: docs.slack.dev has no artifact methods, the help article only says "Code channel APIs will be available to any developer", and code channels (`features.code_channels` manifest flag) appear limited to a list of partner agents for now (checked 2026-10). Artifacts in code channels are collected from what the agent shares there (canvases, files), so the canvases and file attachments above are what this bot publishes. Revisit when an API is documented.
- 
Retention: canvases are user deliverables and are never deleted from Slack. A `bot_canvases` row holds no content and is what keeps a canvas editable, so it outlives thread retention and is deleted after 180 days without use (create, read or edit).
### Agent sessions in DMs
Slack lists agent sessions (one per thread) in the user's sidebar with a title and a status. In DM threads with the bot (`threads.is_dm`, channel type `im`) the bot manages both (`src/pipeline/agent-session.ts`, table `agent_sessions`); channel threads keep the plain processing/active indicator and get no title.
-
**Titles, in the background** (`src/agent/titles.ts`, `titles` queue; no tool: `set_session_title` often ran as a sequential model step of its own before the reply, ~2.5 s). After a DM turn delivered a reply (and wasn't stopped), a job titles an untitled conversation once a human message in it is substantive (greetings and small talk wait, with no model call: pure `isSubstantive` / `sessionTitleDecision`), re-checks a bot title every 3 user turns since it was set (`SESSION_RETITLE_EVERY`; the model answers KEEP unless the main topic clearly changed), and never touches a user-chosen title. One Luna call with reasoning off (≤ 40 characters, sentence case, the conversation's language; the messages are passed as data), usage recorded; jobs are idempotent per thread + turn, and `setSessionTitle` keeps one title per turn (markup stripped). It uses `agents.sessions.rename` (`chat:write`); `agents.sessions.setStatus`'s `title` only applies when a session is created, which intake already did, so it is just the fallback for `session_not_found`.
-
**User renames win.** `agent_session_title_changed` with a human `user` stores the user's title; the bot never renames that session again. Events without a user, from the bot user, or repeating any title the bot set within two minutes (also an earlier one, delivered late) are treated as the echo of our rename. A user rename that lands while the bot's rename is in flight is re-applied afterwards, so Slack shows the user's title too.
-
**Statuses.** A DM turn ends `suspended` instead of `active` while a `send_message` or coding-agent launch confirmation from that thread is pending (Slack: "needs user clarification or a tool approval"); Send / Launch, Cancel or expiry set it `active` again (when they start a mention-like outcome turn, that turn sets `processing` and then its final status instead; a resume that finds the thread lock held keeps the session's note, which the 15 s sweep retries and the thread run re-checks after releasing the lock, so a silent outcome turn can't leave it `suspended`; expiry within ~15 s: a turn that ends `suspended` schedules the check for the confirmation's expiry; a click while the turn still holds the thread lock is re-checked when the lock is released). Side paths that clear a status (stop, intake, a batch that ends without a turn) restore this resting status (`suspended` / `closed`) instead of forcing `active`. `leave_thread` in a DM (DMs always reach the bot, so it doesn't disengage there) ends the turn `closed`: the conversation shows as done until the user writes again, which starts a normal turn (`processing`, then `active`). The prompt asks for it only when the user wraps up.
## Context, images and the web
### Thread context
Each turn includes the thread's parent message plus the newest replies that fit the history window (at most `limits.contextReplies` = 40 replies and `limits.historyTokens` ≈ 8000 tokens, parent always included), a rolling summary of the older replies, and, when relevant, about 5 channel messages from around the thread's parent (`<channel_background>`).
- 
**Channel background only when relevant** (pure, `src/context/channel-background.ts`): included when the thread had at most `limits.channelBackgroundMaxReplies` (3) replies before the turn (a new top-level message or a fresh thread), or when one of the turn's new messages points at something: a bare ping (only mentions/punctuation, no file), `^`, "above", "the last message/post", "what do you think", "wdyt", "thoughts?", "agree?", "is this true", "fact check", "explain this", "tldr", or a short message (≤ 8 words) with this/that/these/those. Otherwise it's other people's unrelated chatter and is left out (not even loaded). The relevance gate keeps its own context.
- 
**Bare pings.** A mention with nothing but @mentions in it, or @mentions plus only a pointer at an earlier message (`^`, `^^`, `↑`, `⬆️`, `:point_up:`, `:point_up_2:`, `:arrow_up:`, "this", "that", "above", "see above"; optionally "pls" / "please" / "?"; pure `barePingKind`), is a bare ping. A plain one gets a turn instruction not to answer `<channel_background>`; if the speaker's most recent earlier message in the thread had content and no bot message came after it (their request went unanswered, e.g. the gate dropped it), the instruction points at that message and says to do what it asks instead of asking "yeah?" (`unansweredEarlierRequest` / `barePingInstruction` in `src/agent/front.ts`); otherwise it helps with what the history makes clear or asks briefly what they need. A pointer ping gets the same unanswered-request handling (a pointer message is never itself the earlier request); without one, it is told to work out which message the pointer means from the history (the one right above, or, only in a thread that just started, the channel message it starts under) rather than being barred from `<channel_background>`. The code never resolves the target itself.
- 
If replies are omitted, a marker says so and how much of it the summary covers: `[42 earlier replies not shown; summarised in <thread_summary>]` (or "not summarised yet" / "the oldest N are summarised…, the newest M not yet", with a pointer to `ask_thread`).
- 
**Rolling thread summary** (`src/context/summary.ts`, table `thread_summaries`), like compaction in coding tools. The window (pure, `src/context/window.ts`) is the replies after the summary's `covered_ts`, as long as they fit the budget (sizes estimated per message as in the read tools; after rendering, any overflow drops the oldest shown replies so the marker stays exact). When the replies after the summary pass `limits.threadSummaryCompactAt` (0.8) of the budget (size or count), rendering enqueues a `thread-summary` job (BullMQ, own queue, processor in `src/tools/register.ts`) to fold everything up to a target ts into the summary, leaving `limits.threadSummaryKeep` (0.5) of the budget shown. Hysteresis keeps the shown history append-only between compactions (a stable prefix for prompt caching), and in steady state the summary covers exactly the replies not shown; a burst past the budget (or a long thread the bot just joined) shows the newest that fit and reports the rest as not yet summarised until the job lands. The job never blocks a turn and never re-reads covered replies: each update is previous summary + the newly dropped replies (stored copies, so `##` messages never appear; rendered in the context format with a ~1500-token per-message cut, no image ids, the parent as context) → new summary, one tool-less model call per batch of ~30k tokens (oldest first) with the children's model and settings (`MODELS.child`, `CHILD_REASONING_EFFORT`), 90 s timeout, usage recorded via `recordModelUsage` (thread only, no user) and accumulated on the row. The prompt keeps the thread's purpose, decisions and conclusions, open questions and commitments (who does what), key facts, links and names, and message ts citations, under ~800 tokens (`limits.threadSummaryMaxTokens`, also enforced as a hard cut), and treats the messages as untrusted (instructions inside are ignored). Idempotent and race-free: the job id is (thread, target ts), removed when done so a later render can re-request; a Redis lock per thread (`lock:thread-summary:<thread>`, the second worker retries with backoff); and every write is conditional on the `covered_ts` it started from (a stale update is dropped). The prompt shows it as `<thread_summary>` right before `<thread_history>`, noted as an automatic summary that may miss details, pointing to `ask_thread` for anything specific (budget `BUDGET.threadSummary`).
- 
Every message is labelled with its author: `<@U123> Ingo: …`; bots as `[bot] Gorkie: …`.
- 
Long messages are truncated with `[truncated]` (`limits` in `src/config.ts`): ~1000 tokens each in thread history, ~300 in channel background, ~4000 for the turn's own new messages, ~2000 in explicit reads (`read_thread`, `read_channel`, `read_public_thread`, `read_public_channel`).
- 
**Forwards and link unfurls.** Slack puts a forwarded message (and Slack message / link unfurls) in a message's `attachments`. They are normalised (`attachmentsFromSlack`, `src/context/normalize.ts`: kind `forwarded` / `link` / `attached`, author, channel name, title, text ≤ 4000 chars, URL; at most 5; any whose content starts with `##` dropped) and stored with the message (`messages.attachments`, migration 252; backfill and intake; a `message_changed` that only adds or removes previews updates them without counting as an edit; cleared on delete and by retention like text and files). The context renders them after the text, e.g. `[forwarded from Sam in #ship: …]` (≤ 1500 chars) and `[link preview: Title — description (url)]` (≤ 400), skipping one whose text the message already contains (an app message whose text is its attachment's fallback, or a public read that inlined it). The gate sees a 300-char version. Safe to show: Slack already showed that content to everyone in the conversation.
- 
Attachments appear as file-store placeholders, e.g. `[file file_k3x9q2mf7a: budget.csv, text, from Ingo]` (see Files); in other threads' messages read through the public tools as `[file: budget.csv]`.
For more, the front agent can call `read_thread(before_ts | after_ts, limit?)` and `read_channel(before_ts | after_ts, limit?)` (current thread/channel only), or delegate a summary of a long thread to a subagent. Both return pages capped by size (`limits.readPageTokens`, ~6000 tokens, estimated at ~4 chars/token; always at least one message) as well as by `limit` (read_thread default 50, max 100; read_channel default 20, max 50). `read_thread` pages backwards from the newest by default or from `before_ts`, and forwards from `after_ts` (the thread's own ts reads from the start); every page starts with its position and how to continue, e.g. `[replies 31–50 of 120 replies; older: read_thread before_ts=…; newer: read_thread after_ts=…]`, and includes the parent only when it reaches the start (pure logic in `src/tools/paging.ts`). `read_channel` pages the same way: the latest messages by default, backwards from `before_ts`, forwards from `after_ts` (walking Slack's newest-first history like `read_public_channel`, so a busy channel doesn't skip ahead); channel totals aren't known, so its header gives the ts range and the cursors, e.g. `[20 top-level messages, oldest first, 1790000000.000100 to 1790003600.000100; older: read_channel before_ts=…; newer: read_channel after_ts=…]`, with "start of channel" / "newest message" when an end is certain (Slack returned fewer than asked; no `before_ts`). The front prompt points "what's been happening in #x" at `read_channel` / `read_public_channel`, and more than a page or two of channel history at a subagent. The bot token only reads channels the bot is in. Other threads (e.g. a search hit that is a thread reply) are read with `read_public_thread(permalink | channel + thread_ts, limit?)`: user token (`channels:history` user scope), the channel must be verified public (cached `conversations.info`, fail closed), parent first then up to 50 replies, `##` messages dropped, forwarded content inlined, no image ids, counted as a Slack search. Other public channels' top-level history is read with `read_public_channel(permalink | channel + around_ts / before_ts / after_ts, limit?)`: same user token and public check, surrounding context around a message or paging older/newer through the channel, `##` dropped, counted as a Slack search. Its pages get the same size cap (`limits.readPageTokens`; around a message it trims the longer side first and keeps the linked message) and the same header with cursors in both directions (`read_public_channel channel=C… before_ts=…` / `after_ts=…`).
- 
**Private-channel links** (`src/tools/private-links.ts`, pure decision `decidePrivateLink`). `read_public_thread`, `read_public_channel` and `ask_thread` with a permalink keep the fail-closed public path, with one exception: a link into a PRIVATE channel is read with the bot token only when (a) the bot is a member (`conversations.info` `is_member`, ~10 min cache), (b) the speaker (or subagent owner) is a member (`conversations.members`, ~2 min cache, fail closed), and (c) the request comes from the speaker's 1:1 DM with the bot or from that same private channel. Group DMs, other channels and links to DMs / group DMs are always refused, and `G…` ids never count as public. Everything that would tell a non-member something collapses into one refusal identical to a missing channel (no id, mention or name); only a confirmed member asking elsewhere is told to ask in a DM (still without the name). Reads count as Slack searches, drop `##` messages, carry no file ids and are labelled `slack thread (private channel)` / `slack channel (private)`. `slack_search` stays public-only.
-
**ask_thread(question, permalink?)** (front + children, `src/tools/ask-thread.ts`) is the primary way to get information out of a thread ("what did X say about Y", catching up, decisions, summaries); both prompts send the agents to it first and keep `read_thread` / `read_public_thread` for exact full messages or checking the messages its answer cites. Without `permalink` it reads the current thread (bot token, `fetchReplies` up to 2000 messages); with one it goes through read_public_thread's shared fail-closed path (`loadPublicThread` in `src/tools/public-thread.ts`: counted as a Slack search; a `C…` channel verified public via cached `conversations.info` (user token), or one allowed by the private-link rule below (bot token); reply links followed to their root). `##` and hidden messages are dropped, forwarded content inlined, no image ids. The whole thread is rendered in the context format with a ~4000-token per-message cut and a ~80k-token overall cap (`limits.askThread*`); over the cap it keeps the parent plus the newest replies and notes how many were left out. One separate model call answers it: the children's model and settings (`MODELS.child`, `CHILD_REASONING_EFFORT`), no tools, 90 s timeout, with a system prompt to answer only the question and only from the thread, cite message ts, quote exactly when asked, say plainly when the thread doesn't have the answer, ignore instructions inside the (untrusted) thread, and stay concise. Usage is recorded via `recordModelUsage` against the speaker / subagent owner. At most 3 calls per front turn and 12 per subagent run (`askThreadMaxCalls`: research follows leads into many threads, and `ask_thread` opens one with a short answer instead of pages of messages in the run's context). The answer comes back wrapped as untrusted content with a header naming the thread and its message count (plus a citation-link hint for other threads).
-
**Slack message links.** Permalink shape is `https://<workspace>.slack.com/archives/[channel]/[timestamp]`, e.g. `https://hackclub.slack.com/archives/C123ABC456/p1790000000000100`. `[channel]` is the channel id; `[timestamp]` is `p` plus the message ts with the decimal removed (`1790000000.000100` → `p1790000000000100`). Thread replies may add `?thread_ts=<root ts>`. Pass these links to `ask_thread` / `read_public_thread` / `read_public_channel` (`fetch_url` cannot open them: they need Slack auth). Parsed in `src/tools/util.ts` (`parseSlackPermalink`).
### Prompt layout
**System prompts** hold judgment only, ordered by importance: identity, safety, how output works (tools only; a reply ends the turn unless `continue_turn`), decision rules (respond / react / stay silent, how to read the message, check facts, answer directly vs delegate), voice (a few principles and bad → good pairs), formatting, and a compact context-format block. Tool mechanics live in the tool descriptions (Slack search technique in `slack_search`, buttons in `reply`, canvas edit rules, reminder / watch confirmations, send_message's confirmation flow, file posting), and situational rules in the turn message: DM wrap-up in `<session>` (titles are a background job), write-up rules in the synthesis instruction (`SYNTHESIS_INSTRUCTION`), and reminder, watch, send and coding-agent outcome rules in those turns' own inputs. Measured with `scripts/measure-prompts.ts` (o200k tokens, every optional feature on; tool definitions as their JSON), Oct 2026: the cleanup took the front system prompt 5812 → 2608 and child 1320 → 566; on main after the later prompt work (fan-out, corrections, format beats brevity, research method) and the removed tools: front 2850 (+ sandbox 296, HuddleFM 310, admin coding section 304), child 775 (+ sandbox 388), synthesis instruction 553 (synthesis turns only); tool definitions front ~9.8k (38 tools), child ~4.6k (18).
Stable parts come first so the provider's prompt cache can reuse them: system prompt, tool definitions, workspace facts. The system prompt is byte-identical across requests (only the admin-only coding-agents section is appended last, for the admin); everything per-turn goes into the turn message, which is ordered from most to least stable so consecutive turns share the longest prefix: `<conversation>` (from cached `conversations.info`, bot token, `src/context/conversation.ts`, ~10 min in Redis: the channel name, its type (public channel, private channel, DM with the bot in the agent container, group DM, plus "Slack Connect (shared with another org)"), the member count, whether people from another org are in it, and the topic and purpose as one capped untrusted line each; left out when the lookup fails), `<thread_summary>`, `<thread_history>` (append-only between summary updates, see Thread context), `<channel_background>`; then speaker memories, `<speaker>` (name, pronouns, job title, current status emoji + text if set and not expired, `Slack language:` (the client locale from `users.info` with `include_locale`; the prompt says to reply in the language the speaker writes in, the locale being only a hint), a `Privileges:` line (bot admin = `ADMIN_USER_ID`, "runs this bot: moderation, kill switches; can launch coding agents" when they're configured; then the Slack workspace admin/owner role, named as a Slack role since it grants nothing in the bot; "none" otherwise), time zone, the channel being viewed in DMs), `<participants>` (up to 10 other people active in the shown thread history and new messages, most recent first, excluding the speaker and the bot: `<@U…> Name — pronouns, title`, ~400 tokens), `<session>` (DMs), `<huddle_dj>`, the subagent snapshot, `<previous_turn_tools>` (user turns right after a turn that used tools, see Turns), `<thread>` (who started the thread and when, its total reply count from the stored copies with how many are shown, or that the turn's message is a new top-level message that starts it; `renderThreadFacts`), `<pending_actions>` (the speaker's own: send_message previews waiting for their Send click with destination and expiry, coding-agent previews not launched yet, live previews waiting for the Cloudflare terms or still claimable, and how many reminders / watches they have running; `src/features/pending.ts`, omitted when empty), `<low_quota>` (one line per per-user limit that is nearly used up: the hourly `takeLimit` windows read without counting (`userQuotaStates`, pipelined `ZCOUNT`s) and concurrent subagents, shown when at most 5 % (at least 1) is left, `lowQuotaLines`; per-turn caps like `ask_thread`'s 3 calls are full at the start of every turn, so they never show); then `<current_time>` (UTC with weekday, e.g. "Wednesday 2026-10-07 01:23 UTC", and the speaker's local time; the clock lives only here, not in `<speaker>`); then the new messages (or synthesis results / scheduled input) and the turn instruction last. Cached input tokens (`usage.inputTokenDetails.cacheReadTokens`, OpenRouter's `prompt_tokens_details.cached_tokens`) are summed into the `turn_timing` counters (`cached_tokens`), recorded per model call in `usage.cached_input_tokens` (front steps, subagent steps, `ask_thread`, thread summaries) and per subagent step in `run_step` events. Measured live (Oct 2026, GPT-6 Luna via Hack Club and OpenRouter direct): across requests only the system prompt + tools prefix (~5k tokens) is served from cache when the turn message differs, whatever its order; within a turn, each step reuses the previous step's whole prompt (e.g. ~33k of ~45k input tokens cached in a 4-step synthesis turn). The order still costs nothing and pays off with providers that cache arbitrary token prefixes. Speaker and participant details come from the shared cached `users.info` lookup (`src/context/users.ts`, `users:read` only, Redis ~1 day, so a status can be up to a day stale; expiry is checked at render time); participant lookups run in parallel and a failed one just leaves that person out. Profile fields are user-written, so they're rendered as untrusted data (`src/context/people.ts`): one line each, newlines/control characters and angle brackets stripped, capped at 80 chars. Each section has a token budget; overflowing sections are summarised or left to the agent's read tools.
### Images
Images are files in the file store (see Files): they appear as `[file file_…: screenshot.png, image, from Ingo — "…"]`, `read_file` puts the image itself into the model's context (downloaded with the bot token, resized to ~1500px on the long side, HEIC and GIF converted, cached), and `ask_file` asks a vision call one question about it. If the model doesn't accept images in tool results, `read_file` returns "image loaded" and the image is appended as a user message instead (`EXTRAS.queueUserImage`, unset for GPT-6 Luna, which was verified to read images in tool results).
### Web search
A client tool, `web_search` (`src/tools/web-search.ts`), backed by Exa's search API (through Hack Club AI's Exa proxy first, then Exa direct with `EXA_API_KEY`), available to the front agent and subagents. (It replaced OpenRouter's `openrouter:web_search` server tool, which cost $0.01 per search plus the result tokens and couldn't be announced or rate-limited before running.) Parameters: `query`; `mode` = `fast` (default, Exa `instant`, ~0.5s, $0.004), `thorough` (Exa `auto`, $0.007) or, for subagents only, `deep` (Exa `deep-lite`, ~4s, $0.012); `num_results` (default 5, max 10); `include_domains`; `start_published_date` (news / "latest"); `full_text` (subagents only: capped page text instead of highlights). Results are numbered title / URL / published date / highlight, wrapped as untrusted content; their URLs feed `runs.sources`. Each call counts towards the per-user hourly web-search limit; failures and timeouts (10s, 25s for `deep`) come back as a short message.
### Slack search
`slack_search` runs Slack's `search.messages` on the user token: about 20 calls a minute for the whole app, shared by front turns, subagents and watches. **Shared limiter** (`src/core/slack.ts`): a sliding window per key in Redis with FIFO waiting: every caller holds a ticket in a queue per priority (`interactive` = a front turn someone is waiting on, ahead of `background` = subagent research and watches; `SlackCallOpts.priority`), sleeps until the window entry that frees its slot expires, and tickets not refreshed for 20 s (dead processes) are dropped; without a deadline a call gives up after 5 minutes. `search.messages` keeps `limits.slackSearchInteractiveReservePerMin` (4) of its 20 slots for interactive calls. A call with `maxWaitMs` fails fast (`SlackBusyError` with the expected wait) when the expected wait is already past its deadline instead of sitting it out; waits over 1 s are logged with their key, and `onWait` reports their start and end (also for 429 pauses).
**The tool** (`src/tools/slack-search.ts`): priority from the role, `maxWaitMs` = `limits.slackSearchMaxWaitMs` (6 s); a full limiter returns a model-facing "rate limited (~Ns)" result pointing at `ask_thread` / `read_public_thread` / `read_public_channel` (separate limits) instead of a silent 35–58 s wait. Identical searches (query, sort, page) share their verified-public, `##`-free, slimmed matches for `limits.slackSearchCacheTtlS` (90 s, Redis; concurrent identical searches in one process share one call), and cached matches are re-checked against the channel-visibility cache (fail closed). The visibility checks (`conversations.info`, `channelVisibility`) use the same priority, `maxWaitMs` and `onWait`: a channel that can't be verified in time is treated as not public (its matches dropped, nothing cached for it or for the search) and the result says how many were skipped because of the rate limit. Other tool reads that could otherwise stall silently in a subagent step (`read_public_thread` / `ask_thread` / `read_public_channel`: the visibility check, `conversations.replies` / `.history`; `users.info` for names) pass the role's priority, `limits.slackToolMaxWaitMs` (15 s) and the run's `onWait`: a busy read returns a "Slack is rate limited right now" result, a busy name lookup just leaves the name out. In a subagent run, results after `limits.slackSearchSoftBudgetPerRun` (12) searches carry an advisory note to read the best threads instead (never a block). While a subagent's search waits a second or more, its card row shows "Waiting for Slack's search rate limit (Ns)" (other methods: "Waiting for Slack's rate limit (Ns)") and then its previous label; `run_step` events record `slackWaitMs`. Watches search as background and fail fast too; a busy check is retried after `limits.watchBusyRetryMs` (10 min) instead of a whole interval. The tool description asks for a few searches per step and for opening the best hits over more keyword variants.
**No semantic search.** `slack_semantic_search` (Slack's Real-time Search, `assistant.search.context`) was removed: the workspace has no Slack AI Search and won't get it, so it was only a keyword search with a lower limit (~10/min). Its guard limit, limiter entries and history-compaction placeholder went with it. The `search:read.public` user scope in `slack-manifest.yml` is now unused; removing it needs a reinstall, so it is left to the owner.
### Fetch URL
A custom `fetch_url` tool, available to both roles, that can never reach local addresses:
- 
http and https only.
- 
Resolve DNS first and reject loopback, private (10/8, 172.16/12, 192.168/16), link-local (169.254/16), CGNAT (100.64/10) and IPv6 equivalents (`::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped).
- 
Connect to the checked IP to prevent DNS rebinding, and re-check every redirect.
- 
Cap at a few MB and ~10 seconds; convert HTML through Readability to markdown.
- 
Use a connection-level library such as `request-filtering-agent` rather than hand-written IP checks.
`fetch_url` can't open Slack permalinks (they need auth); `ask_thread` / `read_public_thread` / `read_public_channel` do that for public channels (and private channels under the private-link rule) using links like `https://hackclub.slack.com/archives/[channel]/[timestamp]`.
Fetched pages and search results are treated as untrusted data.
## Sending on behalf of users
`send_message(destination, text, files?)` can post to the thread's channel, another channel, or a DM. Anything sent outside the current thread is attributed to the requesting user and confirmed first.
**Confirmation (code-enforced).** Before sending outside the thread, the bot posts a `chat.postEphemeral` preview to the requester: destination, the message as it will appear, and Send / Cancel buttons. The pending send is stored server-side and expires after a few minutes; a stale click replies "This expired, ask again."
**The agent hears the outcome.** The tool returns "awaiting confirmation" and the turn normally just ends (the preview is visible, so no "check the preview" reply). Resolving the preview starts a front turn in the pending send's thread with the requester as speaker (`src/features/outcome-turn.ts`): the reused `scheduled` turn kind, whose stored input (`scheduled_turn_inputs`, `source = 'send'`, `source_ref` = the pending id) is a system notice with the destination, the outcome and the drafted message text quoted as untrusted reference material (the agent wrote it, possibly from untrusted sources, and an expired preview was never approved). Outcomes: **sent** (permalink, attachment upload failure if any), **not sent** (cancelled by the speaker, hourly limit, a definitive Slack error such as an archived channel), **expired**. A send-blocked requester gets no outcome turn: the ephemeral tells them privately, and the agent would announce the block in a possibly public thread. **A confirmation never depends on the model:** an outcome turn stores a code-written fallback (`scheduled_turn_inputs.fallback`, migration 181: "sent ✓ <link>", "not sent: <reason>"; none for cancel / expiry) that front.ts posts when the turn ends with nothing visible, fails or is stopped; outcome turns never get the generic "couldn't come up with a reply" / "Something broke" texts. A lost `ensureThreadRun` after the commit is covered by `recoverOrphanedTurns` (pending turns of any kind). Send / Cancel / failures are mention-like turns (status from the start, fallback text if the agent stays silent): the agent confirms in one short line with the link, or acknowledges. An expiry is a non-mention turn: the agent may stay silent, or add a short note. Exactly once per pending send: the status transition (`pending → cancelled/expired`, `sending → sent/cancelled`) and the turn insert commit in one transaction, so double clicks, retried jobs and expiry racing a click start one turn (a unique index on `(source, source_ref)` is the backstop). Entry checks (pause, channel disabled, suspension) and a gone thread (row deleted, root deleted) skip the turn quietly; the pending row still resolves. The expiry sweep runs every minute and only starts turns for previews that expired within the last hour; a click that crashed mid-send is settled by the sweep: sent if the message went out (`sent_messages` is written right after `chat.postMessage`, before uploads and the permalink; else the stored result of the post's idempotency key), otherwise "interrupted". Sweep outcomes are late, so non-mention turns, and there is none when the click path already showed "Sent ✓" itself (its outcome couldn't be recorded; a Redis marker tells the sweep).
**Previews after a click.** A successful Send deletes the ephemeral preview (`delete_original` on the interaction's `response_url`; ephemeral messages can't be deleted any other way) instead of replacing it with a confirmation: the agent's reply confirms it. If no outcome turn will run (skipped) or the delete fails, the preview becomes "Sent ✓ View message" as before. Definitive failures replace it with "Not sent: …"; unknown errors keep it with "Something broke… click Send again" (no outcome yet). Cancel keeps the short "Cancelled." replacement: instant feedback for the click while the agent's acknowledgement is a few seconds away.
**Attribution.** Messages are sent with `chat.postMessage` using `username` (`[bot] on behalf of [user]`) and `icon_url` (the user's profile image), which requires the `chat:write.customize` scope. A context block at the bottom repeats "Sent by @user via [bot]" and holds the report button, so attribution survives in clients that ignore the custom display. The bot must be in the channel, or have `chat:write.public` for public channels. Outgoing sends count towards per-user limits.
## Reports and suspension
- 
**Report button.** Snapshots the message content, sender, destination and permalink into a moderation channel, and replies to the reporter with an ephemeral "Thanks, reported".
- 
**Records.** Every on-behalf-of send stores the message-to-user mapping, so reports keep the original sender even if the message is later edited or deleted.
- 
**Moderation actions.** Reports include a delete button and an action to block the user from the send tool.
- 
**Auto-suspension.** A user reported by more than a threshold number of distinct reporters is suspended until reviewed. Suspension is checked at every entry point, not only sends.
- 
**Reviewer.** Ingo handles all reports.
- 
**Bot reports (`report_user`).** The front agent can quietly report the current speaker (no user id parameter, so it can't be steered into reporting someone else) for clear misuse: harassment or threats (incl. via `send_message`), scams, collecting personal info about others, impersonation, sexual content, deliberate abuse of the bot, or a genuine self-harm concern. Parameters: `category` (enum), `reason` (short, factual, ≤500 chars), optional `message_ts` (must be the speaker's own message; defaults to the turn's latest message). The mod channel gets the category, reason, a snapshot of the message (truncated, pings neutralised), permalinks to the message and thread, and admin-only buttons: Suspend user, Block from send tool, Mark reviewed, Dismiss. Nothing is shown in the user's thread and the bot never tells the user. Stored in `bot_reports` (pending → reviewed/dismissed); at most one per (user, thread) per hour and five per user per day, one per (thread, turn). Bot reports never count towards auto-suspension. Pending ones are kept until reviewed, handled ones go 30 days after review. App Home shows the pending count to the admin.
## Memory
Two kinds: per-user memory, written mostly by a background pass, and a small workspace knowledge base that you approve. Thread memory is the event log itself.
### Per-user memory
**Storage.** One row per fact: `id`, `user_id`, `text`, `source_thread`, `created_at`, `last_used`. Facts not used for about six months expire.
**Background extraction.** When a thread has been idle for about 30 minutes, a Luna pass reads it alongside each participant's existing facts and adds, updates or removes facts. It only runs over conversations with the bot, never over the wider workspace.
- 
Only facts users stated about themselves, never inferences.
- 
A fact from a user's messages can only be written to that user's memory (enforced in code).
- 
No sensitive categories (health, family situations and similar) and nothing about other people's private lives.
**Tools.** The tools take no user ID; the user is always the current speaker.
- 
`remember(fact)` writes to the speaker's memory immediately.
- 
`forget(fact_id)` deletes one of the speaker's facts. Injected facts show IDs, e.g. `[m_42] prefers short answers`.
- 
Facts about other people are stored in the speaker's own memory, attributed: `Ingo says Sam is handling venues`. They never shape how the bot treats Sam.
**Reading.** Only the current speaker's facts are injected into a turn, capped at about 20, labelled as private context for personalising answers, not for reciting. Other participants' memories are never included. When a user's facts outgrow the cap, add pgvector embeddings and a speaker-scoped `search_memory` tool.
**Subagents** never read or write memory. The front agent passes anything relevant in its instructions.
### Workspace knowledge
Facts about the Slack itself (what channels are for, recurring events). The front agent calls `propose_workspace_fact(fact)`, which sends the fact to the moderation channel for approval. Each fact keeps its source thread and proposer. Approved facts are injected into every turn; only Ingo can delete them. Subagent findings reach this through the front agent.
### User control
An App Home tab lists each user's own facts with delete buttons and a "forget everything" option. "Forget X" in conversation uses `forget`. Deletion is a hard delete, including embeddings.
## Reminders and watches
Users can ask the bot to come back later (`src/features/schedule/`, tables in `120_reminders_watches.sql`). All six tools are front-only and take no user id: the owner is always the current speaker, and list/cancel only see the speaker's own items. Listing outside a DM hides the text of items created in other conversations.
- 
**Reminders.** `set_reminder(text, at | in)`: `at` is ISO-8601 (with an offset, or local wall time read in the speaker's Slack time zone, DST-correct), `in` a duration (`2h30m`, `3 days`, `PT2H`). Must be in the future and at most a year out; the tool result echoes the resolved time in the speaker's zone so the reply can confirm it ("ok, fri 9am"). The turn input already carries the speaker's local time. Caps: 20 pending per user.
- 
**Firing.** Postgres is the source of truth; a 1-minute maintenance task polls it (~1 minute precision; no delayed queue jobs to keep in sync with cancels, restarts or Redis loss). A poller claims one due row with `for update skip locked` (status `firing`, a claim id and a 5-minute lease), runs the entry checks and resolves the target, then inserts the turn and marks the row `fired` in one transaction that re-checks its claim: concurrent pollers or a crashed one never fire a row twice. The turn is a `scheduled` turn (kind `scheduled`, input in `scheduled_turn_inputs`) in the original thread with the owner as speaker, so the bot @mentions them in its own voice and can do any work the reminder asks for. At fire time: global pause, owner suspended or deactivated → skipped quietly (status `skipped` + reason). This is deliberate: the reminder is dropped, not postponed (a pause or suspension can last long, and a late reminder is mostly noise); the owner sees nothing. Channel disabled, bot removed from the channel or channel archived → the reminder still reaches the owner, in a DM thread (a one-shot reminder would otherwise be lost). Thread root deleted → the same DM fallback (rooted at a short bot note, idempotent per reminder). The entry checks run against the channel actually used, so a DM fallback is checked against the DM (e.g. a suspension hidden behind a disabled channel still skips it). Watches differ: a check in a disabled / left / archived channel is skipped with the baseline kept, and resumes when the channel is usable again. A thread row removed by retention is recreated. A failed attempt (Slack/DB error) is retried with backoff (1, 2, 5, 10 min; `retry_at`, so one blip can't burn every attempt at once); five failed attempts → `failed`, and the owner gets a short plain DM that the reminder couldn't be delivered (idempotent per reminder).
- 
**Watches.** `create_watch(source, target, criteria, check_every_hours?, expires_in_days?)` checks a web page (SSRF-safe fetch; normalized text snapshot + hash, line diff), a web search query (new result URLs) or a Slack search query (public channels only, verified and fail-closed, `##` dropped; only matches newer than the last seen ts, excluding the owner's own messages, bots and the watch's own thread) every 6 hours by default (min 1h). The baseline is taken at creation. When a background check finds candidate changes, a cheap no-tools Luna call (reasoning off, usage recorded for the owner) judges them against the owner's criteria; only a "yes" starts a `scheduled` turn in the watch's thread (not a mention: the agent may still stay silent) with the findings as untrusted data. At most one notification per check (unique per check number), at most 3 per watch per day (the baseline is kept while capped), entry checks every check, and every check counts against the owner's hourly fetch/search limits. Watches expire after 30 days at most (said when created); the snapshot is dropped as soon as a watch ends. Caps: 5 active per user.
- 
**App Home** lists the viewer's pending reminders and active watches with Cancel buttons. **Retention:** fired/skipped/cancelled reminders and ended watches (with their notifications) are deleted 30 days after they finish.
## Huddle DJ (HuddleFM)
The bot can DJ Slack huddles that run HuddleFM, through HuddleFM's bot API (https://github.com/ingoau/huddlefm/blob/main/docs/bot-api.md): JSON commands DMed to the HuddleFM user, replies threaded under them, events as DMs (`src/features/huddlefm/`, `190_huddlefm.sql`). Off unless `HUDDLEFM_USER_ID` is set; the bot's own user id must be in HuddleFM's `INTEGRATION_USER_IDS`. The feature follows gork's auto DJ (functionality only, own implementation) with these differences: all state lives in Postgres/Redis (any worker), song picks are verified, and the auto DJ learns from what people queue and skip.
- 
**Tools** (front only): `huddle_dj_mode(enabled, channel?, auto_dj?, chatter?, vibe?)` asks the host for control (`request_control` with add/add-bulk/remove-own/manage-queue/skip/pause/volume/clear; never end-session or settings) or releases it / cancels a pending request; `huddle_dj(channel?, commands[])` runs music commands in order (status, search, add by query/queries/reference with `play_next`, remove, move, shuffle, clear, skip with count, previous, pause, resume, seek, volume); `huddle_dj_settings(auto_dj?, vibe?, chatter?)`. The huddle is the current channel by default; another channel (or one named from a DM) needs the speaker to be a member (`conversations.members`, cached, fail closed). Anyone in the channel can use them once the host approved. `huddle_dj` calls count against a per-user hourly limit.
- 
**Transport.** Commands go through `slackCall` (idempotency keys from the turn/tool call or job) with Slack-proof JSON (`<`, `>`, `&`, `/` as JSON escapes). HuddleFM messages in the DM are routed by intake before anything else (never stored, never a conversation): replies land in Redis under the command's ts, and the sender polls that key, so no reply waiter lives in memory and a reply that beats `chat.postMessage` is simply already there. Work that waits on replies never runs in the slack-events processor (the replies come through it): it runs in the `huddlefm` queue.
- 
**Sessions.** One `dj_sessions` row per huddle channel: `pending` until the host answers (a silent request is dropped after 6 minutes), `active` after `grant_accepted`, deleted when DJ mode ends (turned off, declined, expired, revoked, `session.ended` / `session.suspended`, a lost-grant error, or an hour without any answer from HuddleFM). A request cancelled while pending is remembered, and a late approval of it is released right away.
- 
**Notices.** Things people should hear about (host answered, session ended or lost, a song someone queued failed to download, chatter) start an outcome-style `scheduled` front turn (source `huddlefm`) in the thread where DJ mode was asked for, with the requester as speaker and a `<huddle_dj_notice>` as input. The session update that makes it true is the transition, so a duplicate delivery announces once; grant and end notices have a code-written fallback. Chatter (off by default, at most one line per 4 minutes) and failure notices (at most one per 2 minutes) may stay silent.
- 
**Auto DJ** (on by default). Events, tool calls and a 1-minute sweep ask for a sync (a `huddlefm` job deduplicated per channel, at most one running plus one waiting). A sync reads `status`, stores the playback snapshot shown to the agent in `<huddle_dj>`, and when fewer than 2 songs people (or the bot) queued are waiting (HuddleFM's own autoplay picks don't count), asks Luna (low reasoning, structured output, usage recorded for the requester) for a few more candidates than needed, given the vibe, now playing, queue, recently played, songs people queued themselves, auto picks people skipped, its own recent picks and the origin thread's last messages (untrusted). Repeats are dropped in code, and each search result must match the title and artist with no unwanted variant (karaoke, cover, sped up…) or the candidate is skipped. A top-up that adds nothing or fails, and an auto DJ pick that fails to download, count as misses: back off (1 min doubling to 15) until one of its picks actually plays; a new vibe or turning auto DJ back on retries at once. A `huddle_dj` call stops at the first command HuddleFM doesn't answer, and a `request_control` that fails after the tool stopped waiting is announced. Entry checks (pause, suspension, disabled channel) apply to the requester before any model call. The relevance gate is told when the bot is DJing in the thread's channel, so "skip this" reaches it.
## Coding agents (Cursor)
The bot's admin (`ADMIN_USER_ID`) can ask the bot to change its own code: a Cursor Cloud Agent works on the bot's repo and opens a PR (`src/agent/cursor/`, `160_cursor_agents.sql`). Off unless `CURSOR_API_KEY` and `CURSOR_REPO` are set (`CURSOR_REF` default `main`, optional `CURSOR_MODEL`). Uses Cursor's Cloud Agents API v1 (public beta; https://cursor.com/docs/cloud-agent/api/endpoints).
- 
**A subagent kind.** `subagents.kind = 'cursor'` plus the Cursor agent id; each run (card row) is backed by Cursor runs (`cursor_runs`). So a coding agent shows on the plan card like a subagent (details "Coding in Cursor…", the elapsed time, the Cursor agent and PR links as task sources), its result arrives through the same synthesis turn, and the front snapshot marks it `[coding agent, Cursor]`.
- 
**Tools.** `spawn_coding_agent(title, instructions)` (front only; only offered in the admin's own message turns). `message_subagent` / `cancel_subagent` dispatch on the kind. **Admin-only in code:** start, steer and cancel are refused unless the speaker is the admin and the feature is configured; bulk cancels by anyone else (old "Stop all" buttons) skip coding agents. Other users' messages never reach Cursor. The "Coding agents" prompt section is appended to the system prompt (after the shared, cacheable base) only in the admin's turns when the feature is configured; nobody else's turn learns the tool exists. It says plainly that the current speaker is the bot admin and may launch coding agents (prod: the admin was refused as "admin-only" three times), and `<speaker>` shows the same in its `Privileges:` line. Both the section and the tool description also say plainly that coding agents are only for changes to or questions about the bot's own code and behaviour, never for deliverables for people (websites, pages, apps, scripts, documents, research), even when the admin asks: those are made with `create_file` / `reply(files)`, canvases or subagents (replay: a coding agent was proposed to "build portfolio HTML" for a user). It is proposed only when the admin asks for a change or an investigation; musings and feedback ("should probably…", "at some point…") get a brief acknowledgement with no promise to change itself. **Admin messages that land next to a results turn:** a synthesis or scheduled turn sees, in its turn instruction, the user turns already queued in the thread ("Queued after this turn: <@U…>: [ts]…") and is told to leave them to their own turn, which runs right after with the admin as speaker and `spawn_coding_agent` available. Chosen over offering the tool in a synthesis turn when the admin's message is among its inputs: `cursorInstructRefusal` stays exactly as strict (only `user` turns, whose input is the speaker's own words, can start or steer a coding agent), and the queued turn already exists, so no new scheduling path is needed; it also stops results turns from answering other people's queued messages twice.
- 
**Prompt injection.** Everything a turn's model reads (thread history, other people's messages, fetched pages, search and subagent results, watch findings) can carry instructions, so: (1) starting, steering or resuming a coding agent is refused in code (`cursorInstructRefusal`, in the tool functions, not just the tool list) unless the turn is a `user` turn whose speaker is the admin. Synthesis turns (subagent results, which any thread participant can influence by steering the admin's model subagents) and scheduled turns (watch findings, reminders) can't, even though their author is the admin; cancelling stays allowed anywhere. (2) **Admin confirmation before launch:** `spawn_coding_agent` only proposes. The task goes into `pending_coding_agents` (15-min expiry) and the admin gets an ephemeral preview with the exact title and task as they will be sent (plain text, so formatting can't hide anything), the fixed rules code adds, and Launch / Cancel. Only `ADMIN_USER_ID` pressing Launch starts it (checked in the click handler); the claim is atomic (a double click launches once), the pending id doubles as the client-supplied Cursor agent id, stale clicks get a short reply, and the tool result tells the front agent the launch awaits confirmation. The launched agent gets a plan card of its own in the thread (no turn; synthesis goes to the admin). Follow-ups to an already-launched agent from the admin's own user turns need no button (the prompt says to pass only the admin's own words).
- 
**Instructions.** Code wraps the front agent's task in a fixed preamble: this repo is the bot, follow CLAUDE.md; never touch `.github/workflows/` or any other CI / repository-policy config (anything under `.github/`, other CI systems' files; also enforced on GitHub); the same agent may edit code or explore/search the codebase (no separate search kind); keep changes focused; run `pnpm typecheck` / `pnpm test` and a review subagent only when the agent judges them necessary (skip for README/docs-only or pure exploration); PR only (`autoCreatePR`), never push to the base branch or merge; end with a summary. Follow-ups restate the rules.
- 
**Steering.** Cursor can't inject a message into a running cloud run (create-run answers `409 agent_busy` while one is active; the SDK's `run.steer()` is local-only). A steer is queued in the subagent inbox (card note `↪ next: …`) and sent as a follow-up Cursor run (same conversation, branch and PR) as soon as the current run finishes; the card row stays running until Cursor is done. `message_subagent` on an idle coding agent starts a new run (↻) backed by a follow-up on the same Cursor agent.
- 
**Polling, exactly once.** No public HTTP endpoint (Socket Mode), so no webhooks: the `agent:cursor-poll` maintenance task (every 10 s) claims one due run at a time (`for update skip locked`, claim id + 10-minute lease renewed before slow steps, like reminders; finishing re-checks the claim inside `finishRun`'s transaction) and reads the Cursor run. Running → card details + next poll; finished with queued steers → follow-up run; FINISHED → result (PR link, branch, Cursor's summary) and `finishRun` → synthesis; ERROR / EXPIRED / cancelled elsewhere → error run. Creation is idempotent (client-supplied `bc-<uuid>` agent id; a retry gets `409 agent_id_conflict` and reuses the agent). Only a definite rejection (4xx other than 408) of a launch or follow-up deletes the local rows; on a timeout / network error / 5xx Cursor may have accepted it, so the rows stay and the poller looks the agent up (a follow-up records the previous run id, `after_run_id`, so it never adopts the old run; nothing new within 2 min → the run fails). A finish deferred for steers that arrived meanwhile is retried at most 3 times (`inbox_defers`), and a cancel-requested run always ends (cancel_subagent also drops unseen steers), so a run can't be re-polled forever. An agent that never gets a run times out like any other (`cursorRunMaxMs`). Nothing lives in worker memory, so restarts don't matter. Transient API errors back off (up to 5 min); a vanished agent fails the run.
- 
**Deleted thread root.** Cancelling a coding agent is the admin's call, so a deleted root doesn't cancel running ones (model subagents are cancelled as before). Instead they move to a DM thread with the admin (`rehomeCodingAgents`, from the intake's root-deleted handling): a short note roots the DM thread ("your coding agent '…' from a deleted thread continues here", idempotent per agent), and the subagent, its active run and a new plan card are re-homed there, so steering, cancelling and the result's synthesis turn all work in the DM. Idle ones stay where they were.
- 
**Timeouts.** The stale-heartbeat sweeper and shutdown hook skip coding agents (no worker loop); they have their own limit (`limits.cursorRunMaxMs`, 3 h): the Cursor run is cancelled and the run fails. At most `limits.cursorMaxActive` (3) run at once.
- 
**CI check.** The Cursor API doesn't list changed files, so after a run the PR's files are read from GitHub (REST "list pull request files", only for a PR in `CURSOR_REPO`; optional `CURSOR_GITHUB_TOKEN` for private repos). Any change to CI or repository-policy config (anything under `.github/`, e.g. workflows, actions, CODEOWNERS, dependabot.yml; CODEOWNERS elsewhere; other CI systems' config such as `.gitlab-ci.yml`, `.circleci/`, `.buildkite/`, `Jenkinsfile`, `.travis.yml`, `azure-pipelines.yml`) is flagged loudly in the result (card output "⚠️ touches CI config"); if the check fails, the result says so.
- 
**Results.** The synthesis turn shares the PR link and a short summary; the prompt says never to claim it's merged. Rows follow the subagent retention.
-
**Launch outcomes.** Like send_message previews (see Sending on behalf of users): Cancel, a failed launch (definite Cursor rejection, deleted thread) and expiry start one outcome turn for the admin (`source = 'coding_launch'`, a `<coding_agent_outcome>` system notice; expiry as a non-mention turn the agent may leave silent). A successful Launch has none (the plan card and the later synthesis cover it) and deletes the preview; it only turns into "Launched ✓ …" when the card couldn't be posted. Outcome turns are `scheduled` turns, so they can't start or steer coding agents.
## Code sandboxes
Subagents can run code in an isolated Linux sandbox (`src/sandbox/`, migrations `250_sandbox.sql`, `251_sandbox_first_use.sql`, `253_sandbox_updated_at.sql`; full plan, spike results and deviations in docs/sandbox.md). Off unless `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` are set: then there are no tools, jobs or App Home section, and nothing touches Modal.
- 
**Provider.** Modal Sandboxes behind a small `SandboxProvider` interface (`provider.ts`, `modal.ts`; E2B is the documented fallback). Images are pinned in code: a work image (Playwright's Ubuntu image with Node 22 and Chromium, plus Python 3.12 with pandas/numpy/matplotlib/pillow/openpyxl/requests/bs4, pnpm, git, jq, sqlite3) and a deploy image (Node + pinned wrangler); `pnpm sandbox:images` prebuilds them (the first work build takes ~13 minutes). Commands run as an unprivileged `sandbox` user in `/work`, with a minimal environment: no secrets, nothing from the worker's env.
- 
**Who and when.** The front agent delegates: `spawn_subagent` tasks take `sandbox: true` (the field only exists when the feature is configured), set only when code must run: installs, data processing or charts, analysing uploaded files, a headless browser, multi-file builds or a live preview. A single file the front agent can write itself (a page, script, CSV, text) is `create_file` with no sandbox, and research needs none. The front prompt's sandbox section (only when configured) lists running code, data / file processing and live previews, so "what can you do" includes them. Only those subagents get the sandbox tools (registered for children; `child.ts` drops them otherwise) and a 30-minute run cap instead of 10. Access is checked at spawn and on every tool call: the `sandbox_disabled` kill switch (admin bypasses), the monthly budget (nobody bypasses), then the admin or the App Home allowlist, then (unless `sandbox_access_mode = allowlist_only`) a verified Hack Club identity: `auth.hackclub.com/api/external/check` with `verified_eligible` or `verified_but_over_18`. Only a boolean is stored (7 days; it stays the "last known positive"), negative answers are cached in Redis for minutes with the reason kind only, and errors, 5xx and unknown values never count as unverified and are never cached. The person gets the reason in an ephemeral (at most one per 15 minutes); the model only learns that it isn't available for them (budget and kill switch may be said plainly), and every refusal text tells it to do the task without a sandbox wherever it can (e.g. `create_file`), now and without asking first (`SANDBOX_FALLBACK`; prod: a one-file site was given up instead).
- 
**Lifecycle.** One sandbox per subagent, created by its first sandbox tool call (a subagent that never runs code costs nothing; a Redis lock per subagent makes parallel calls share one), reused while live, paused ~45 s after its run ends when no other run of the subagent is queued (`limits.sandboxRunEndPauseMs`, a delayed pause job that is skipped if the sandbox was used again meanwhile; idle live time counts against the user's daily minutes and the budget), else by the sweep after 5 idle minutes (filesystem snapshot + terminate: Modal has no native pause), resumed by the next follow-up's first call, destroyed when the subagent expires or is cancelled (the 30-second `sandbox:sweep`). A sandbox the provider lost (its 45-minute lifetime, a crash) is replaced on the next call, and the tool tells the model its files are gone. `sandbox:reconcile` (10 min) destroys provider sandboxes whose row is gone, ended or moved on to another box, and marks rows the provider no longer has as lost, but never mid-transition: a row in any non-terminal state (incl. `pausing`, whose box is still listed while it snapshots) or changed within the last 2 minutes (`updated_at`, a trigger, migration 253) keeps its box, and an orphan with a row, or a transition stuck for 15 minutes, is only touched under the row's lock (try-lock: a held lock means a transition is running). Pause transitions are conditional updates (before, a pause in progress, whose box is still listed while it snapshots, was destroyed and ended `lost`). Nothing lives in worker memory.
- 
**Tools** (children): `sandbox_exec` (bash, 60 s default / 300 s max, output cut to head + tail with the full output in `/work/.last/`; 200 per user per hour; abort on cancel kills the process group), `sandbox_read_file` (text pages; images come back as images, so a subagent can look at its own chart or Playwright screenshot), `sandbox_write_file` (≤ 200 KB text), `sandbox_import` (a file-store file into `/work/in/`, through `resolveFile`'s access rule; ≤ 50 MB), `sandbox_export` (a sandbox file into the file store as a deliverable, ≤ 25 MB, listed with the run's result for `reply(files)`), `request_preview` (see below). Output from the sandbox is wrapped as untrusted content; `sandbox_exec` thread events store the command, exit code and duration, never output. The file store's 5 MB cap stays for everything else (`createFile` / `loadFileBytes` take a scoped `maxBytes`).
- 
**Network.** Open internet minus private, loopback, link-local (incl. cloud metadata), CGNAT, benchmarking, multicast and reserved ranges, as an IPv4 allowlist of the complement (`egress.ts`, unit-tested; extra denies via `SANDBOX_EGRESS_DENY`). Modal's allowlist is IPv4-only, so IPv6 is unreachable. Ports can't be filtered (known gap; mitigated by quotas, the gate and Modal's abuse handling).
- 
**Quotas and budget.** Reserve 0.5 core / 1 GiB, limits 1 core / 2 GiB; 2 sandboxes in active use per user and 8 overall (creating / resuming, or running for a subagent with a queued or running run: a finished subagent's sandbox stays live until the idle pause but doesn't count, and when idle live ones would push the total over a cap, the oldest are paused at once); 30 live minutes per user per UTC day. Every live segment is a `sandbox_usage` row priced at Modal's sandbox rates ($0.1419 per core-hour, $0.024 per GiB-hour, at the limits: an upper bound). The month's spend is max(our estimate, Modal's metered cost for the environment); at `SANDBOX_MONTHLY_BUDGET_USD` (default 20; dev ~5) or when Modal's whole-workspace cost reaches `SANDBOX_WORKSPACE_CREDIT_USD` (28, under the $30 free credit dev and prod share) every running sandbox is paused and new ones are refused until the next month, with a clear message; the mod channel gets a notice at 80 % and at the stop. A start needs room for one maximum segment.
- 
**Live previews** (only with `PREVIEW_SECRET_KEY`). `request_preview(dir, title)` only checks the site (an `index.html`, ≤ 1,000 files, ≤ 5 MiB each, ≤ 25 MiB) and stores it as an internal file-store bundle; deploying is code, after the run completes: entry checks, kill switches (`sandbox_previews_disabled`), access, budget, then the requester's consent: an ephemeral naming Cloudflare with its Terms and Privacy Policy and Accept / Cancel (recorded per terms version; 30 minutes to answer). The bundle is checked again in Node (limits; a form scan refuses password, card and similar fields in HTML and scripts), every HTML file gets a banner ("Preview built by … for @user · expires HH:MM UTC · not affiliated with any site it imitates") and a robots meta tag, `_headers` and a fixed Worker add `X-Robots-Tag: noindex` and `form-action 'none'`, and `wrangler deploy --temporary` runs in a fresh deploy sandbox with a fresh HOME. The temporary account's token and the claim URL are stored AES-256-GCM-encrypted and nulled when the preview ends. The bot posts "Live preview of *title* for @user: <url> · expires …" with **Get claim link** (only the requester; the URL comes back ephemerally and never reaches the model, events or logs) and **Report** (mod channel, where the admin can Take down with the temporary token; also in App Home). Previews live 60 minutes (`sandbox:previews` marks them expired and updates the message); 5 per user and 30 overall per day. The front agent only says a preview is coming; the link arrives on its own. A live `wrangler deploy --temporary` run confirmed that Worker + assets deploys, the ND-JSON `deploy` record (URL in `targets`), the `wrangler-temporary-account.toml` keys and the token takedown before a claim. Still open: a server-side fetch of a fresh preview got a 403 Cloudflare challenge, so whether browsers see the site, and the banner / headers, are unverified (docs/sandbox.md §9, §10).
- 
**Disclosure and App Home.** Everyone sees one line in App Home on where the data goes (code and files to Modal in the US for the task; previews to Cloudflare after accepting its terms), and gets the same as a one-time ephemeral note on their first sandbox use (`sandbox_first_use`, migration 251). The admin sees the month's spend and live sandboxes, the kill switches, the access mode, the allowlist (add with a user picker, remove) and live previews with Take down.
- 
**Retention.** Sandbox filesystems live while their subagent does (≤ 24 h idle) and snapshots are deleted with them (7-day TTL otherwise). `sandboxes` and `previews` rows go 30 days after they end, usage segments after 62 days, HCA rows not re-checked for 30 days; month totals have no personal data and stay.
## Safety, limits and reliability
### Limits
Per user: messages per hour, concurrent subagents, searches and fetches, and on-behalf-of sends. Per thread: max concurrent subagents. Per run: 10 minutes (`limits.runMaxDurationMs`; 30 for sandbox subagents), 1M cumulative tokens across its model steps (`limits.runMaxTokens`, mostly served from the prompt cache; 400k ended Slack-heavy research after ~10 steps) and 50 steps; at the token or step cap, and 90 s before the time cap (`WRAP_UP_BEFORE_TIMEOUT_MS`, `src/agent/child.ts`), the run is told to stop using tools and report what it has, including the leads it didn't get to (a timed-out run used to fail with no result at all). Per front turn: `ask_thread` 3 calls (12 per subagent run), `ask_file` 12, `create_file` 20, and the lookup guard (see Agent roles). At GPT-6 Luna's prices these exist mainly to stop abuse and runaway loops, not to control budget.
### Kill switches
A global pause flag, per-channel disable for channel owners, and a per-user block list (shared with suspension).
### Reliability
- 
**Event deduplication.** Dedupe on `event_id` and the `X-Slack-Retry-Num` header so Slack retries never cause double replies.
- 
**Idempotent side effects.** Every send, reaction, upload and card post carries an idempotency key derived from its event, checked before acting.
- 
**Liveness.** Workers heartbeat during runs; a sweeper marks stale runs as errored and updates their cards. Clean shutdowns mark in-flight runs errored before exit.
- 
**Model or API outages.** Post a short "Something broke, try again" rather than going silent.
### Observability and testing
- 
Trace every turn and run: prompts, tool calls, gate decisions, tokens, latency, cost. PostHog LLM analytics, Langfuse or similar.
- 
Build evals from saved threads (with permission), especially steer versus new task, silence, and ambiguous follow-ups. Replay them after prompt changes.
- 
Develop against a separate Slack app in a test workspace.
### Retention
The community is mostly teenagers, so keep only what's needed. Thread event logs, subagent histories and traces are deleted after 30 days. Stored copies of Slack messages are deleted when the original is deleted. Rolling thread summaries are derived from stored messages, so they go with them: with the thread, once the stored copy of the oldest message folded in passes 30 days (the summary is then rebuilt from what is still stored), and when a reply they cover is deleted in Slack (checked by the daily retention job before the deleted copy's content is dropped). Files the bot made are deleted 30 days after creation; uploads in the file store go with message retention and as soon as their Slack message is deleted (see Files). Per-user memory is the exception: it persists until deleted by the user or expired by `last_used`.
