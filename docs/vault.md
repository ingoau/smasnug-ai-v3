# Vault: per-user credentials

Issue #36. Code: `src/features/vault/` (store, approvals, tools, App Home), sandbox side in `src/sandbox/browser/`
(`vault.ts`, `vault-files.ts`), connectors in `src/features/connectors/` (docs/mcp-custom-connectors.md).
Off unless `VAULT_SECRET_KEY` is set (32 bytes, base64: `openssl rand -base64 32`). Keep the key outside Postgres;
losing it makes every stored credential unreadable.

## What it stores

`vault_credentials` (migration 357), one row per (owner, name):

| kind | secret | used by |
|---|---|---|
| `token` (UI: "API key / secret") | `{ value }`; meta: `domains`, `header` + `scheme` (default `Authorization: Bearer`) | `fetch_with_credential` (front + children), `sandbox_use_credential` |
| `login` | `{ username, password, totp? }` (TOTP seed or `otpauth://` URI; codes are generated by the bot, `totp.ts`) | `browser_fill_credential`, `sandbox_use_credential` |
| `browser_session` | `{ state }` (agent-browser state: cookies + localStorage) | `browser_save_session` / `browser_load_session` |
| `connector` | API key or OAuth state (client registration, PKCE verifier, tokens) | MCP connectors |

`meta.domains` ties a credential to websites (host or any subdomain, `hostAllowed`). A credential **without a
website** can't go into any request the bot makes: it only reaches a subagent's sandbox as a file
(`/work/.vault/<name>`), and the agent is told to use it in commands without reading it.

Encryption: AES-256-GCM (`src/sandbox/preview/crypto.ts` layout) with a per-user key, HKDF-SHA256(master, user id)
(`crypto.ts`). A key for one user opens nobody else's rows.

## Who can save and use them

- **The user**, in App Home: "Add login" / "Add API key / secret" open a modal (name, website, username + password
  + optional 2FA key, or secret + how to send it, a note for the agent). Delete per credential; the last uses are
  listed under it.
- **The agent**: `save_credential` (a secret already in the conversation; never overwrites) and, in a subagent,
  `sandbox_save_credential` (from a sandbox file, so the value never passes through the model). The owner gets a
  private notice either way.
- **The agent asks the user**: `request_credential` posts a private card with "Add it", which opens the same modal
  prefilled. The secret never appears in the thread. Front agent: an outcome turn says when it was added or declined;
  a subagent waits (up to `limits.vaultWaitMs`).

Identity (`identity.ts`): only Slack-verified identity counts. On the front agent, the author of a **user** turn
(not reminders, watches, outcome or synthesis turns); in a subagent, its owner. Never a tool argument, a mention, or
whoever steered the subagent. That last case (anyone may `message_subagent`) is why each use needs the owner's
approval.

## Approvals (`approvals.ts`)

Every use (a request, a browser fill, a sandbox file, loading a saved session, a connector action in prompt mode)
posts a card only the owner sees (ephemeral in the thread, else a DM) saying exactly what will happen, with **Allow
once**, **Allow for 10 min here** (a grant for that credential in that thread only, `vault_grants`) and **Deny**.
Only the owner's click counts. Cards expire after `limits.vaultApprovalTtlMs`.

- `wait` mode (subagents): the tool polls the row and carries on.
- `outcome` mode (front agent): the tool returns "awaiting approval"; on the click, code runs the action
  (`registerApprovalExecutor`) and the result reaches the agent as an outcome turn (source `approval`), like
  send_message. These tools are hidden in `!p` private turns, since the outcome turn answers in the thread.

## Keeping secrets away from the model

- Secrets are injected by code into one request header (`safeFetch` with `authOrigin` + `authHeaders`, so they're
  dropped on a cross-origin redirect; a request with a body never follows redirects), one browser field (over
  stdin), or one sandbox file (removed before every pause snapshot and when the run ends).
- Output scrubbing (`scrub.ts`): exact matches of a secret, URL-encoded, base64 or JSON-escaped, become
  `[redacted:<name>]` in tool output. Secrets handed to a subagent stay registered for it (Redis, by id), so all its
  later sandbox and browser output is scrubbed. Best effort: a model that deliberately transforms a secret can still
  get it out; approvals and domain pinning are the real controls.
- Modal submissions: ingress seals the form state of `vaultm:` / `connm:` modals (`transport.ts`) before queueing,
  because BullMQ keeps finished jobs in Redis.
- Never logged, never in thread events; the audit log (`vault_audit`) records what, where and when only.

## Retention and privacy

Credentials stay until the owner deletes them. Audit rows: 90 days; decided approvals: 7 days (`pruneAudit`).
Withdrawing privacy consent (App Home) deletes the user's whole vault, connections and audit log
(`deleteAllVaultData`, `deleteConnectorData`).

## Risks (accepted for v1)

- A person steering someone else's subagent could try to misuse the owner's credential; the card names the exact
  site, field or command, and grants are per thread.
- Inside the sandbox, code can read `/work/.vault` files and send them anywhere; the card says so.
- A typed browser value briefly appears in agent-browser's own argv inside the sandbox.
- A DB breach without the master key yields only ciphertext.
